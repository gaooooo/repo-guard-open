跑 `repo-guard audit`，然后按下面的规则解读结果。

## 为什么要有这个命令

红线是**人写的意图**（"这个接口外部仍有调用方，改名等于让对方 404"），
静态分析永远推不出来，所以必须人写。但人写的指针会腐烂，而且**review 发现不了**：

reviewer 能判断"这条该不该加"，但验证不了
「paths 写全了没」「evidence 行号还准不准」「protects 的符号是不是早就改名了」。

所以：**人写意图，机器验完整性。**

## 三类腐烂，分别怎么处理

| audit 报什么 | 含义 | 该怎么办 |
|---|---|---|
| **守空气的规则** | `protects` 里的符号在代码和 SQL 里都找不到 | 符号被改名或删了。要么更正符号名，要么删掉这条规则。**留着最危险** —— 它让所有人以为有保护 |
| **有覆盖缺口** | 符号实际出现的位置不在声明的 `paths` 里 | 那些位置是**后门**：agent 在那里改动不会被拦。按 audit 给的建议补进 `paths` |
| **evidence 失效** | `evidence` 的行号指不对了 | 只影响人看，不影响判定。顺手更正 |
| **拦不住（无 protects）** | 没声明 `protects` | 这条规则只能靠 prompt 自觉，运行时拦不住。补上受保护标识符 |

## 输出要求

1. 先给一句总结：**几条规则、几条在守空气、几处后门**。
2. 逐条列出要改什么，**直接给出改好的 JSON 片段**，不要只说"建议补充"。
3. 如果一条都没问题，说清楚"扫了几个源码文件、几个 SQL 文件"——
   让人知道这个"没问题"是在多大范围上得出的。

## 不要做的事

- **不要自己动手改 `redlines.json`。** 那是人的意图声明，改它要过 review。
  你的产出是改好的片段，由人贴进去。
- 不要因为一条规则在守空气就推断"红线机制没用"。腐烂是必然的，定期体检才是解法。

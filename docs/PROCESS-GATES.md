# Beta 开发过程控制 · 开发方案

状态：待确认的开发方案，尚未实现。图谱接入已完成，本方案只扩展 repo-guard 的开发指导、任务范围、增量审查与验证证据；不重写 code-atlas。

## 1. 本期目标与取舍

目标不是“多拦几次”，而是让 AI 完成本次需求的同时，不额外扩大改动范围或系统复杂度。

本期交付四项：

1. 内置简洁开发基线：最简实现、复用优先、少抽象、按真实边界校验、不夹带优化。
2. 任务范围收敛：明确目标、非目标、验收，区分必要配套改动与无关改动。
3. 增量审查：围绕任务期间实际 diff 看范围扩张、疑似重复、无意义拆分，结合已接入图谱。
4. 真实验证：区分执行过、成功、失败、运行中、证据未知、已过期，不把工具调用当成通过证明。

Beta 原则：一个项目配置入口；一条默认流程；小任务不强制长方案或审批；新增控制默认指导/提醒；不自动清理历史债，不默认循环修复。

**本期不做：**复杂红线 DSL、每条规则风险分级、冻结策略重设计、文件预算硬门、自动审批链、跨机器审计平台、通用规则执行器、新的复杂度 AST/图谱引擎。已发布契约与安全边界不能因为“最简实现”被删减。

## 2. 开发者的使用方式

~~~bash
# 目标：一个入口完成图谱准备和 Beta 配置。保留现有 --ws / --with 行为。
repo-guard init --write --ws myproject --with ../backend

# 正常向 AI 提需求；结束前也可由人主动做过程自查。
repo-guard review
~~~

首次接入只需确认“改前查影响面的目录”，有特殊要求再补规则；检查命令从已有工程配置建议生成，没有则留空并说明。开发者不必学习 Hook、L0–L6、severity、check.kind 或打开多份 JSON。

AI 的默认路径：读要求 → 明确目标/非目标/验收 → 查已有实现 → 做必要改动 → 对实际 diff 自查 → 执行对应检查 → 如实交付。

例如“列表新增状态筛选”：

- 目标：筛选控件、请求参数、后端过滤正确联动。
- 非目标：替换状态管理、重构请求框架、整理所有列表页。
- 验收：筛选结果正确、清空可恢复、分页符合约定。
- 合理配套：接口类型、后端过滤、对应测试；不因跨了三个文件就判为越界。

简单文案/样式修改只需一句范围说明；只读问答、诊断、审查不自动启动编码任务，不因此要求“修复”发现的问题。

## 3. 配置：一个入口，两层继承

### 3.1 拟新增配置形状

全局模板：插件 `layers/repo-guard.json`。
项目差异：业务仓 `.codebuddy/repo-guard.json`。

~~~json
{
  "version": 1,
  "enabled": true,
  "publicLayer": ["src/components/", "src/utils/"],
  "rules": [
    { "id": "PRJ-001", "rule": "页面文案沿用本仓 i18n 写法，不新增一套文案方案。" }
  ],
  "checks": [
    { "id": "typecheck", "argv": ["npm", "run", "typecheck"] },
    { "id": "test", "argv": ["npm", "test", "--", "--runInBand"] }
  ]
}
~~~

示例命令必须替换为真实工程支持的命令；init 不照抄示例，不发明脚本，不执行检查命令来探测。

| 字段 | Beta 语义 | 可配置主体 |
|---|---|---|
| version | 格式版本，固定 1 | P 模板维护者 / J 项目 |
| enabled | 是否启用新增 Beta 控制，不关闭宿主权限或旧规则 | P / J |
| publicLayer | 修改已有文件前查影响面的目录前缀；不是禁止改，也不是图谱扫描范围 | J，以本仓真实目录为准 |
| rules | 额外开发指导；id 稳定，rule 文字必填，可选 enabled=false 关闭继承条目 | P / J |
| checks | 项目检查入口，以 argv 表示原生命令；默认工作目录为所属仓根 | P / J |

不提供任意“规则 → 自动 Shell”执行机制，不新增 protects 或人审风险字段。文字规则只指导，不假装具有机器强制能力。

### 3.2 内置机制与可调整基线

- 内置机制：加载、合并、事件接线、去重、快照、证据状态和图谱适配，只由框架维护者改源码。
- 内置开发基线：使用全局模板里的稳定 id 文本，项目可按 id 补充/覆盖/关闭。Beta 不实现 locked 或放宽审批。
- rules 按 id 覆盖，项目缺字段继承；新 id 新增；全局/项目同层重复 id 报错，不静默覆盖。
- checks 按 id 覆盖，argv 整体替换，不拼接。项目显式 checks=[] 表示本仓没有配置检查命令。
- publicLayer 由项目明确值优先，空数组表示不启用此目录手续；全局不要预设“适用于所有仓”的目录。
- 项目文件缺失：新 Beta 控制不参与运行时；已有配置仍按既有逻辑执行。
- 字段格式错误：CLI doctor/init 显式报错；Hook 不崩、不拦用户，只产生去重诊断。字段来源和实际生效值可在 doctor 看见。

### 3.3 初始化与旧配置的边界

新仓 init --write 只生成这一个可编辑配置，不默认铺 redlines / standards / process-gates / human-review 等多文件。图谱本机绑定和索引仍由已实现模块维护，既有 --ws/--with 不改。

为了避免 publicLayer 存两份，新模式通过读取适配器把 Beta 配置转换成内存 RepoFacts，公共层判定仍复用现有实现；不为它再写 repo-facts.json。原 RepoFacts 的旧读取行为对旧仓保持。

已有 Beta 文件：不覆盖用户字段；图谱准备仍幂等，新增模板内容通过运行时继承体现。

旧仓：保留所有旧文件和已有改动，不自动删除/迁移红线。新文件中的公共层优先级需显式展示；原红线、范围、权限策略继续独立生效，Beta 的 enabled=false 不代表那些策略关闭。旧项目已开硬门时，doctor 必须说明“高级约束仍在”，不能宣传整仓都只提醒。

新 Beta 控制用统一注入和提醒入口；同一核心公共层要求不注入两遍。旧高级模式继续有明确入口，但不作为首次使用者的必学路径。是否完全迁移旧高级配置，属于后续红线/门禁专题，不在本轮暗中实现兼容迁移器。

## 4. 系统内置简洁开发基线

使用短文本而非几十条治理字段，建议十条：

1. 只实现本次明确需求，不添加推测的功能。
2. 优先修改已有实现；新增方法、组件前查是否已有合适实现。
3. 采用满足当前需求且符合本仓习惯的最简单方案，不为未来预留框架或扩展点。
4. 只为真实职责、复用或测试边界拆分，不为了缩短行数制造文件碎片。
5. 不新增仅转发、没有实际职责的封装层；不为单一调用建立通用框架。
6. 校验集中在真实边界，内部已有保证不重复校验。
7. 不新增无依据的兼容、默认值、重试和重复兜底，不把错误伪装成成功。
8. 不夹带无关重构、重命名、格式化或依赖调整。
9. 范围外问题先说明，必要配套修改说明因果；明显歧义或破坏性选择交给人。
10. 按本次验收验证，未执行、未覆盖和失败的检查明确说明。

外部输入、鉴权/租户隔离、资源释放、有效超时、数据一致性/幂等不是“多余防御”。删除已有校验、减少错误处理同样要依据，不能以“代码少”为唯一理由。

注入预算作为实现常量：首版以基线约 600 token、项目指导约 400 token 为预算，任务摘要按需另控约 300 token；不暴露为开发者必填阈值。内置基线优先保留，项目指导独立预算，超限完整条目截断并明确告知；不截断半条否定句。复用现有 token 估算与按完整行裁剪，不新增模型摘要调用。用户原话永不被截断或改写成新需求。

## 5. 任务约定与状态

### 5.1 两个拟新增 MCP 工具

只增加两个工具，不引入审批平台或多 Agent 编排：

**task_context**：建立/更新/读取当前任务的短约定。

~~~json
{
  "action": "begin",
  "goal": "列表增加状态筛选",
  "nonGoals": ["不重构请求框架"],
  "acceptance": ["清空筛选可恢复列表", "筛选与分页联动正确"],
  "paths": ["src/pages/orders/", "src/api/orders.ts"]
}
~~~

- 支持 begin / update / status。同会话只维护一个活动编码任务，返回 taskId；update 携带该 id。
- begin 在写代码前调用；不以关键词猜“这是不是新任务”，UserPromptSubmit 只注入提醒。
- 已有活动任务时 begin 不静默重置；status 或 update 延续它，明确 replacement 才建立新基线。
- paths 是预计范围，不是硬白名单。它不自动拥有修改/部署授权。
- 新代码范围之外的合法配套修改可说明理由并 update；AI 的理由属于自述，不代表用户批准。
- task_context 不接受“用户已同意”布尔值，不让模型自签高风险授权；此类确认仍在对话/宿主权限层完成。
- 缺 task_context 时写操作不被新机制拒绝；首次写前采集保守基线并标为“任务未明确”，交付前提醒，不把一次遗漏变成开发死锁。
- 读、诊断、审查中可建立只读约定，但不把发现问题当成写代码授权。

**process_review**：只读生成本任务过程审查包；CLI 对应 `repo-guard review`。

- 返回任务约定、增量 diff、预计范围差异、有效图谱记录、验证状态、待判断问题。
- 不接受模型传入“检查已经成功”作为证据；不执行用户代码、不自动修复、不提交。
- AI 收到审查包后按固定问题清单进行语义自查。机器指标与模型结论分开呈现。
- process_review 接受可选 taskId；MCP 有活动任务时优先显式传该 id。CLI 对应 repo-guard review --task <id>；不传且无可靠会话时展示当前工作树，标明无任务归因，不用“最后一个当前会话”猜。

**会话关联的具体接线：** task_context(begin) 先生成随机 taskId 和待关联约定/快照，结果返回该 id；新增匹配本插件 task_context 的 PostToolUse 分支，使用事件真实 session_id 将任务挂到该会话。后续 update/review 显式传 taskId，Hook 校验原绑定；同一任务不能被另一会话静默认领。若宿主不提供该事件，标记“未关联”，仍可按 taskId 手动审查，但不自动归因写入。旧 adoptSessionFor 的“最近活跃仓指针”不作为新任务证据。process_review 的 PostToolUse 同样消费本次 taskId/快照回执，才记录“本次版本已自查”，不能仅凭工具名标记完成。

不额外新增 verify MCP 执行器：避免把配置命令隐藏在 MCP 子进程里绕过宿主的权限/可见执行流程。检查仍通过正常 Bash/工程工具运行。

### 5.2 状态放哪里

放在 `$HOME/.repo-guard/` 的会话状态区域，不写入业务仓，不让开发者维护任务 JSON。状态属于临时数据，不是第三层规则继承。

至少记录：taskId、sessionId、目标/非目标/验收、预计仓/路径、基线、成功写入、图谱查询、验证事件、已提示项、更新时间。

begin/replacement/更新失败不能覆盖其他会话；并发更新复用现有锁与原子写语义。缺 id 或解析失败时不共享 _nosession 编码任务。上下文压缩后只重注入活跃约定和证据摘要，不重建基线。过期状态依既有生命周期清理。

## 6. 基线与改动归因

**当前 HEAD 不是任务起点；git diff HEAD 也不等于 AI 本次改动。** 用户可能已经有未提交/暂存改动，人工和其他会话也可能同时修改。

Beta 采用“任务开始清单 + 目标文件延迟快照”，不创建 Git commit/stash/worktree，不重置 index，不完整复制仓库：

1. begin 保存 HEAD、index/工作树脏文件清单、预计路径内源文件内容 hash；只记录不修改。可接受新的仓路径清单，不把父目录整个当作单仓。
2. 第一次写前保存实际目标的 before 内容；目标原本不存在记为新文件。调用失败不计为成功修改。
3. 写成功后保存 after hash/计数；同文件多次编辑以最早 before 和当前内容生成净变化，不重复累计中间补丁。
4. begin 时未覆盖到的目标，或 hash 在首次写前已有变化：标“首次观测/可能外部修改”，不称精确任务起点。
5. 下一次写前发现内容与上次 after 不符：记录人工/其他会话干预，归因不确定；不自动覆盖或恢复文件。
6. 新增文件后删除，净变化不计新增；重命名保留来源/目标关系，识别不足时按删除+新增展示，不声称精确归因。
7. Shell 修改、格式化、测试生成文件等：用任务前后工作树变化补充发现，来源标“未被写工具确认”。复杂命令不从字符串猜所有目标。
8. 若不确定外部改动，报告“本任务期间观察到”，不报告“AI 越界”。缺 git 时仅支持已观察文件，不模拟完整仓审查。

大型/二进制/不可读文件按实现预算只存 hash 和状态，不存完整 before，也不对它做复杂度结论。首版资源上限建议单文件快照 2 MiB、单任务原文总计 16 MiB；目标 hash 枚举也设超时/总量预算。这些只限制本机采集资源，不是限制开发的质量门；采样或预算到达要显式标“审查范围不完整”，超预算照常允许合法修改。

快照可能包含敏感源码：目录/文件限制本机私有权限，不记录凭据值到 metrics，不自动上传；原始内容按任务过期清理，日志只保留规则号、路径与结果。不能把整份源码塞进长期记忆或报表。

## 7. 过程接线与失败行为

| 时机 | 处理 | 是否能阻断 | 谁控制 |
|---|---|---|---|
| SessionStart | 检查项目是否启用，注入短基线/项目指导 | 新增机制不阻断 | P 接线 / J 规则 |
| UserPromptSubmit | 提醒目标/非目标/验收，必要时查同类；不默认 begin | 绝不 continue:false 吞提问 | P |
| task_context(begin/update) | 建立短约定与基线 | 数据校验失败返回说明，不阻断写 | AI 调用 / 用户任务决定范围 |
| PreToolUse 写工具 | 记录写前快照；既有公共层手续保持；新范围提示不挂此处 | 只有既有明确门参与 | P / J 公共层 |
| PreToolUse 命令 | 可明确匹配 checks 时采集检查前版本指纹；不执行检查 | 不阻断、不注入正常命令提醒 | P / J checks |
| PostToolUse 写成功 | 记录净变化，提示本次超长/范围线索 | 只提醒、同项去重 | P |
| PostToolUse 命令 | 识别真实检查、退出/完成状态，写证据 | 不阻断 | P / J checks |
| PostToolUseFailure | 记录失败，不因“有执行”升级成功 | 不新增失败阈值硬门 | P |
| PostToolUse 图谱 | 复用 Atlas 回执，记录任务关联和参考计划 | 不二次建图 | P / code-atlas |
| PostCompact | 重注基线与任务摘要，不重复任务初始化 | 不阻断 | P |
| process_review | 前台收集 diff/图谱/检查证据，输出审查包 | 默认只读报告 | AI/开发者主动调用 |
| Stop | 检查是否缺自查/验证；默认只提醒和留痕 | 新 Beta 不驱动续跑 | P |
| CI / permissions | 合并与危险操作 | 工程/宿主决定 | J / U，插件不夺权 |

原有 Stop conform/engineeringCheck 的阻断行为对旧仓仍须如实说明。本期新仓默认不打开旧高级门。新 review 将 conform 放前台消费；旧模式保留原接线，不宣称“所有 Stop 都不续跑”。

提醒去重键至少包含 taskId、repo、文件/规则、证据版本。正常连续编辑不每次刷同一句；内容出现新的实质问题可重新提示。任务说明与规则摘要不可无限叠加。

Hook 失败、快照失败、缺 Atlas、不支持的工具形态：新增 Beta 机制 fail-open，并显示能力缺口。失败不转成功，也不静默删除旧门。只支持真实注册的工具名/参数，CLI/IDE 两套写工具都要覆盖；REPL 中嵌套工具的事件是否暴露必须真机验证，未暴露时按盲区说明，不承诺完全覆盖。

## 8. 写前复用与写后增量审查

### 8.1 复用不只是完成手续

保持 Atlas 作为唯一图谱引擎：

- impact：已有代码的上游影响；trace 不代替它。
- reuse/hot：候选方法和组件；similar：参考家族/页面骨架。
- review：改动影响、疑似重复、契约与回归建议。
- conform：参考计划与实际实现是否偏离；保留合理不一致的解释，不一律要求照抄。

任务摘要显示“参考了什么 / 实际复用了什么 / 没复用为什么”。AI 必须阅读候选后判断适用性；没有候选是“未查到”，不是“全仓不存在”。选择结果先作为自述记录，不用字符串相似就认定实现正确。

本期扩展 Atlas review 的回执/文本结构消费，不扩展它的复杂度识别算法。普通 Atlas review 仍以指定 base（默认 HEAD）为基准，它包含用户先前的改动；过程报告将其标“工作树图谱审查”，与延迟快照形成的任务增量分开。历史命中不算 AI 新引入；混合归因只列待确认，Beta 不强行改造 Atlas 为任务补丁引擎。

### 8.2 机器和语义分工

| 检查 | Beta 做法 | 不做 |
|---|---|---|
| 范围扩张 | 列预计范围之外的实际净变化，要求与需求关联 | 仅凭文件数越界硬拦 |
| 超长文件 | 延续已有增量提醒，原本超限不催拆 | 超限强制拆分/自动重构 |
| 文件碎片、转发层 | 展示新增文件/函数线索，由 AI读 diff 判断职责 | 用短文件数量判定“过度拆分” |
| 重复实现 | 消费 Atlas 候选，要求阅读、选择/不复用理由 | 再写相似度引擎，或强行抽公共函数 |
| 函数复杂度/嵌套 | 有现成 lint/检测结果则引用；无则语义检查并标来源 | Beta 新建跨语言 AST 计量系统 |
| 冗余校验/兜底 | 对照输入边界、已有保证和真实错误路径审查 | 用 if/try/catch 个数硬判多余 |
| 契约/调用问题 | Atlas review/contracts 并呈现推断与盲区 | 把静态通过说成业务正确 |

语义自查固定五问：

1. 每处改动是否服务目标/必要配套？
2. 是否重复实现已有能力？
3. 新增文件、抽象、分支是否有当前需要？
4. 校验/兜底是否重复或掩盖错误？
5. 验证是否覆盖验收，而不只是编译？

AI 在当前主线程完成这五问，无默认子 Agent、无额外模型服务。不能机械回答五个“是”；有问题给证据位置、原因和最小修正。无关历史问题记录为后续，不进入自动修复清单。

## 9. 验证证据设计

### 9.1 不自动执行配置命令

checks 的 argv 是工程入口描述，不是授权脚本。AI 用正常 Bash/宿主执行工具运行，使具体命令可见、受原有权限限制；前台报告可建议，但 Hook 不执行 lint/test/build，也不在 Stop 起进程补验证。

init 仅建议已存在的脚本名与技术栈命令，不声明它们必然安全或有测试覆盖。项目自定义脚本可能写数据/发布；执行前仍按实际任务与宿主权限处理。

### 9.2 可采信的状态

- running：只有启动/后台 task id，还没有完成结果。
- passed：明确识别 checks 的实际命令、仓 cwd，得到终态 exitCode=0，运行覆盖代码版本未失效。
- failed：终态非零、信号中断、工具明确错误；timeout 单独注明。
- unknown：仅关键词、输出片段、缺退出码、复杂 shell无法定位子命令、无法关联会话/仓。
- stale：执行后相关源码/配置发生变化，原成功结果不证明当前版本。
- not_run：配置了但没有记录；checks=[] 为 not_configured，不等于通过。

Bash 的普通 PostToolUse 本轮已经可提供 exitCode；不得延续“钩子看不到任何退出码”的旧注释。缺字段时仍 unknown，不能默认成功。`echo test`、`grep test`、`npm test || true` 不算 passed。命令标准化只支持明确的 argv 与可证明的单次 cd 链；复杂 shell不猜成多个通过。

检查前记录相关源码指纹，完成后再核对；检查自己生成的非源码产物不自动污染指纹，忽略规则继承工程已有约定，不随意排除测试/配置。文件变化预算无法完整计算则证据 freshness=unknown，而不是 fresh。

后台启动结果不能作通过证据；只有宿主返回真实终态且可关联原命令时升级。Beta 不主动轮询宿主私有 task id；没有可用终态事件时建议前台重跑，保持 unknown/running。

模型自述“测试通过”不更新 evidence。原始命令若含令牌、输出若含敏感内容，不存到 metrics；只存入口 id、仓、状态、时间和版本指纹。通过一条命令只证明该条命令，不代表其他 check 或端到端验收通过。

### 9.3 交付呈现

固定短格式：完成内容、必要配套修改、实际执行结果、未覆盖/待确认事项。

例如：typecheck passed，test not_run；已人工验证筛选与清空，后端异常返回未验证。没有测试覆盖时必须说清，不从绿色构建推导字段安全。

Stop 上的 context 不保证再给 AI 一轮，因此真正的 review/验证必须在交付前主动运行。Beta 不借 continue:false 弥补此限制，避免自动续跑和任务膨胀。

## 11. 开发步骤与每步交付

### P1：统一入口与开发基线

交付：新配置模板/加载、init 薄配置、doctor 来源、短基线注入；无新配置时不影响旧模式。

验收：开发者只确认 publicLayer、可选 rules/checks；重跑不覆盖；不铺一堆治理文件；相同要求不双重注入。

### P2：任务上下文与增量观测

交付：task_context、只读/编码区分、延迟快照、净变化记录、并发隔离与压缩恢复。

验收：读问答不产生写任务；写失败不算修改；用户原有改动和外部干预不算 AI 确定越界；小改动无需人逐步批准。

### P3：前台过程自查与图谱联动

交付：process_review / repo-guard review、任务/工作树两种 diff 标注、五问语义检查、图谱参考选择与问题线索。

验收：无后台模型/子 Agent；不在写前建图；不自动重构；已有重复先给候选和理由，不靠“查过”就宣称复用。

### P4：真实验证证据与交付收口

交付：checks 命令与终态匹配、证据新鲜度、后台 unknown/running、一次性缺证据提示、文档和隔离回归。

验收：关键词不作成功；代码变更让旧验证失效；无默认 Stop 续跑；前端端到端/后端契约验证缺口可清楚呈现。

各步先查已有方法和图谱影响，改函数后运行 Atlas review 与相关回归；不顺手修正图谱已有误报算法。阶段名是实施顺序，不是引入四套配置或四次手工初始化。

## 12. 测试与验收矩阵

| 用例组 | 必测场景 |
|---|---|
| 配置/接入 | 新仓一文件、全局继承/覆盖、显式空数组、坏 JSON、重复 id、重跑不覆盖、旧高级门展示 |
| 指令/任务 | 小任务、纯问答/诊断、不明需求、范围外发现、必要跨仓配套、同会话换任务、压缩恢复 |
| 基线/归因 | 开始时已脏/已暂存、失败写、同文件多次写、新增后删除、二进制/大文件、Shell 改动、人工/并发修改 |
| 图谱/审查 | 有效/失败/歧义回执、无 Atlas、同名跨仓、无参考、有参考不适用、已有重复、历史命中不归因本次 |
| 验证 | 前台 0/非0、启动失败/超时、后台未完成、输出含“passed”但无终态、echo/grep test、||true、跑后改代码、配置入口变化 |
| 噪音/行为 | 正常连续编辑不刷屏、存量超长不催拆、无默认自动修复、Stop 缺证据只提醒、Hook 异常不阻塞 |

工程检查：沿用 npm run check，并将新增过程回归接入同一检查；验证不碰真实仓，采用临时 HOME/仓/Atlas 工作区。验收脚本覆盖失败与不误伤，而不仅是“能够拦截”。

人工抽验四种任务：小 bug、前端筛选跨后端、公共工具修改、单函数新需求。观察 AI 是否先找现成实现、是否不夹带优化、最终 diff 是否可读、未验证项是否真实。

评价使用同任务同提交的对照样例：功能验收通过率、无关改动、新增概念/重复实现、人工可读性、额外提醒和开发者放弃率。文件数/行数只作描述指标，不作为自动质量分。没有真实数据不承诺减少多少行或提升多少百分比。

## 13. 关键风险与边界

- 范围与“最简”是语义问题：Beta 辅助审查，不宣称机器保证。
- 多人共享工作树无法精确归因：明显标记不确定，不以不完整观测处罚。
- 缺 task id、超预算、缺工具：降级而不是伪造成功或任务上下文。
- 新配置与旧高级约束共存：统一展示但不悄悄降级已有红线/权限；全面迁移另做。
- checks 可执行工程脚本：不由 Hook/MCP暗中代执行，不把配置当成授权。
- 过长指导和自动审查容易膨胀任务：短基线、按需展开、前台一次自查、无默认续跑。
- 规则数不等于控制效果：以功能正确且没有额外复杂度/范围扩張作为最终标准。

## 14. 设计依据与本仓现状

参考 YAGNI（https://martinfowler.com/bliki/Yagni.html）：避免推测性功能和未来扩展，不以此省略必要测试和合理演进。

参考增量 Harness 实践（https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents）：一次推进可验证行为，明确交接状态，避免一次做太多与提前宣称完成；不照搬它的多文件脚手架、自动提交或多 Agent 架构。

本仓已有：图谱薄适配和回执、会话状态、注入预算、写前守卫、历史超长不催拆、默认关闭的范围/循环/交付门。本期复用它们，不从零造框架。

代码依据：src/hooks/atlas-track.ts:12（有效图谱回执）、src/hooks/index.ts:570（增量超长提醒）、src/gates/delivery.ts:54（执行前关键词弱证据）、src/runtime/session-state.ts:214（旧会话指针认领，不能直接复用为新任务授权）。

现有 delivery 在执行前按关键词记录弱证据；现有 scope 主要是静态路径/文件预算；现有 Stop conform 可阻止结束。它们不等于本方案的任务基线、语义范围审查与强验证证据。不要把“已有字段/文档”当成“新流程已实现”。

# 既有过程门禁说明（旧高级模式）

以下保留现行高级配置说明，便于旧仓维护；不是本次 Beta 的首次接入步骤。以顶部开发方案为新功能目标，勿把两套默认行为混为一谈。

范围：**ReAct 内、机器拍板**。管的是这次写入的手续——查过没、改没改出范围、转没转圈、跑没跑过校验。

不是红线（不数 `protects`），不是人审（不问「这个符号能不能动」），也不是合并门禁（不代替 lint / CI / `git commit` 权限）。

项目文件：`.codebuddy/process-gates.json`（`repo-guard guard init --write` 从 `layers/process-gates/process-gates.json` 拷过去，已存在不覆盖）。

---

## 一句话

出厂只有一件硬事：**改公共层已有文件，本轮没查 impact → deny**。其余默认关，要开闸才上场。

---

## 和别的层怎么分

| 层    | 问的是           | 过程门禁做不做                                                      |
| ---- | ------------- | ------------------------------------------------------------ |
| 工程事实 | 公共层在哪、行数上限    | 只用 `repo-facts.json` 的清单，不在这里填目录                             |
| 红线   | 哪个符号不许少       | 判定挂在同一条写前链上，但规则写 `redlines.json`；`admission: false` 时不上膛     |
| 人审   | 何时把决定权交回人     | 不做。`stopConditions` 是 T4 注入；红线命中后的 ask 是 `human-review.json` |
| 图谱   | 影响面 / 同类 / 热点 | 门禁只要求「本轮查过没」，不在 hook 里建图                                     |
| 合并门禁 | 进主干前过没过       | 不做。Stop 不硬拦 `git commit`                                     |

---

## 默认就在跑：公共层 impact

|      |                                                                          |
| ---- | ------------------------------------------------------------------------ |
| 拦    | 文件在 `repo-facts.json` 的 `publicLayer` 下 **且已存在** **且** 本会话没查过该文件的 impact |
| 放    | 新建公共层文件；公共层之外；已经查过 impact 的同一文件；仓库外路径                                    |
| 开关   | **不受** `admission` 控制。没 `repo-facts.json` → 不拦，并明说守卫未生效                  |
| 落点   | `PreToolUse` 写工具（Write / Edit / MultiEdit 等）→ `permissionDecision: deny` |
| Bash | 命令看起来像在用 shell 写公共层 → **只提醒不拦**（路径可能是变量拼的，硬拦误伤率不可接受）                     |

查过之后放行也记一笔，用来看这道门有没有在做有用功。

影响面为 0 ≠ 可以删。拒绝文案每次都堵这句，并给出 MCP / 斜杠命令 / CLI 绝对路径三种查法（只写 `impact` 模型会搜不到工具，改去 grep）。

---

## 写前判定链（`PreToolUse`）

按代价排序。模型已经卡住时，再让它去查影响面没有意义，所以循环在最前。

1. **循环门**（要开 `loop`）
2. **红线 / 禁改**（红线另见红线层；禁改要开 `admission`）
3. **范围门**（要开 `admission` + `scope.enabled`）
4. **新建文件的图谱强制**（要开 `admission` + 对应子开关，且人写了 `pathPatterns`）
5. **公共层守卫**（核心，不受 admission 控制）
6. **规范 `require_tool`**（要铺了项目层 standards；管核心守卫覆盖不到的新建 / 非公共层路径）

这一步只允许 deny / ask / 什么都不输出。提醒不挂在写前，否则每次正常写文件都变成干预。

异常一律 fail-open：hook 崩了等于没这道门，不能把人的写入弄失败。

---

## `process-gates.json` 里有什么

### 注入 `inject`（默认开，只推不拦）

SessionStart / PostCompact 推使命、禁忌、停止条件、红线摘要。  
UserPromptSubmit 按任务路由注入「去读这些文件」。

**禁止** `continue: false` 吃掉用户提问。内容来自 `facts.json`，不来自本文件的长文。

### 准入 `admission`（默认关）

打开之后，下面几项才可能硬拦。公共层 impact **不**靠这个开关。

#### 禁改 `noRefactor`

路径 glob 命中即 deny：「这段代码脏得有原因，先找人确认」。不问人。

模板里的示例带 `confirmed: false`。当前引擎**不读**这个字段，真正总闸是 `admission`。打开准入前先改成本仓真实路径，或把示例删掉。

#### 范围 `scope`

- `allowlist`：名单外的文件不让改（即使改得对，review 也不会预期看到）
- `maxFiles`：单会话涉及文件数上限。这是**失控探测器**（一次任务改到第 15 个文件通常意味着理解错了），不是为了省事。建议 10–20。已改过的文件不重复计数。

#### 新建图谱强制

只管**新建**文件；已存在的文件走 impact，不走这三条。

| 开关                      | 要求本轮先查                           |
| ----------------------- | -------------------------------- |
| `newPageSimilar`        | similar（前端：同类页；后端：同类 handler/接口） |
| `newComponentHot`       | hot（仓内高扇入，别重造）                   |
| `newComponentLibSearch` | lib search（组件库有没有现成的）            |

`repo-guard guard init --write` 会按本仓**已有目录**填 pathPatterns（前端 views/pages/components，后端 handler/logic/router 与 pkg/utils）。enabled 默认 false。硬拦还要打开 `admission` 和对应 enabled。人可以改 glob；已有非空 patterns 不会被覆盖。

「查过」按**会话 + 仓库**记，不按文件记：similar / hot / lib 回答的是「这类东西仓里怎么写」，查一次对整批新建都适用。按文件记是骚扰。不能拿 A 仓的查询放行 B 仓。

### 循环 `loop`（默认关）

捕捉失控，不是捕捉一次写错。

| 项        | 默认阈值 | 行为                                        |
| -------- | ---- | ----------------------------------------- |
| 同一调用指纹重复 | 3    | deny                                      |
| 连续失败     | 3    | deny                                      |
| 同文件写失败   | 2    | deny                                      |
| 迭代预算     | 80   | **只观测**。插件拿不到宿主的 round 序号，Stop 上给摘要，不阻止停止 |

指纹取路径和命令，**不取文件内容**：改一个字再试一次是卡住时的典型动作，把内容算进指纹会永远到不了阈值。

阈值不要调到 2：第 1 次可能是笔误，第 2 次是没看懂报错，第 3 次才是出不来。

### 交付 `delivery`（默认关）

Stop 时看本轮有没有写文件、命令里像不像跑过校验。

- 改了文件但没跑 lint/test/build → **提醒**（默认不 deny）
- 同一会话同一句只提醒一次，防止 Stop 死循环
- `engineeringCheck: "block"` 才阻止停止，仍然不硬拦 `git commit`

证据是弱的：只看命令文本里有没有 `lint` / `test` / `build` / `tsc --noEmit` 这些词，**不能看过没过**。文案必须说清这一点。

真要拦提交：宿主 `permissions.ask` 配 `git commit` / `git push`（合并门禁 · Agent 侧）。

### 诚实信号 `signals`（默认关）

会话结束记一笔近似结论（写了没、失败没、跑过校验没）。插件看不到宿主内部的 success / max_iterations，报表上按近似读，不要当成平台那套 finalReason。

### 治理留痕 `governance`（默认开）

deny / ask 等事件写到 `$HOME` 下，**不进你的 git**。只观测。

### 审查 `review`（默认关）

预留：达到风险等级时拉审查 agent。不是合并门禁的 G-01～G-07。

## 明确不做

- 不预测、不代替 G-01～G-07
- hook 里不建图（写前只有十几秒预算；缓存 miss 就放行）
- 不把 lint 失败写成 Stop 硬拦
- 不把「意图不清」收成手续（写 `facts.json` 的 `stopConditions`）
- 不数标识符出现次数（那是红线）

## 怎么开

1. `repo-guard guard init --write` 铺 `.codebuddy/process-gates.json`（已存在不覆盖）
2. 先确认 `.codebuddy/repo-facts.json` 的 `publicLayer` 是人看过的
3. 需要硬拦红线 / 禁改 / 范围 / 新建强制时，把 `admission` 设为 `true`，再改对应子项
4. 循环、交付同样：先开总闸，再改阈值
5. `repo-guard guard show` 看实际生效；总闸关着时子项 `enabled: true` 也不生效

`verify-hooks` 里有一组「删掉过程门禁配置后，公共层守卫仍在、提问不再注入」的用例：项目层不存在 = 除核心 impact 外零行为变化。

# 多仓演进

> 现状是**单仓**，而且是"隐式单仓"——仓库根从 cwd 推出来，全程只有一个值。
> 这篇文档说清三件事：这个假设的准确边界在哪、要支持多仓得反转哪个语义、
> 以及跨仓影响面在零服务端下能做到什么程度。

deerclaw 支持接入多仓，是因为它有服务端把 N 个仓的图谱都建好放在一起。
这个插件没有服务端，所以不能照搬那条路 —— 但也不必照搬，见第 3 节。

---

## 1. 当前单仓假设的准确边界

### 1.1 仓库根在哪算出来的

三个入口各自算一次，然后一路当参数传：

| 入口 | 代码 |
|---|---|
| hook | `src/hooks/index.ts:131` `repoOf(input)` = `findRepoRoot(input.cwd \|\| process.cwd())` |
| CLI | `src/cli/index.ts:146` `findRepoRoot(process.cwd())` |
| MCP | `src/mcp/server.ts:164` `findRepoRoot(process.cwd())` |

`findRepoRoot`（`src/runtime/paths.ts:38`）从起点往上找第一个锚点
（`.git` / `package.json` / `go.mod` / `pom.xml` / `build.gradle` / `pyproject.toml`），
返回**单个字符串**。图谱同样是单值：`CodeGraph.repoDir`（`src/graph/types.ts`）。

好消息是边界收得很干净：

- 仓库内的配置与缓存都在 `<repo>/.codebuddy/`（`paths.ts:56-63`），**靠路径天然按仓隔离**
- `toRepoRelative`（`paths.ts:89`）对仓库外的路径返回 `null`，调用方按"不管"处理 ——
  这个"不管仓外"的姿势正好是多仓路由的现成基础
- 埋点记录里已经有 `repo` 字段（`src/runtime/metrics.ts:64`），`governance` 报表天然可按仓聚合

所以多仓不是重写，是**把隐式单值变成显式维度**。

### 1.2 三种"多仓"，现状各不相同

| 形态 | 现在的实际行为 |
|---|---|
| **monorepo**（一仓多包） | 基本能跑，但有个坑：`ROOT_ANCHORS` 把 `package.json` 也算锚点，在 `packages/foo` 里跑会停在**子包**而不是仓根，图谱范围被悄悄截断（见 1.3） |
| **多根工作区**（父目录下挂 repo-a / repo-b） | 不会崩，但会**静默当成一个大仓**（见 1.3） |
| **跨仓影响面**（改 A 仓接口，炸 B 仓调用方） | 完全做不到。这是 deerclaw 多仓的真正价值所在，见第 4 节 |

### 1.3 两个已经存在的行为（不是崩，是静默地不对）

**① `findRepoRoot` 在子包停住。** 锚点是逐层遍历的：只要当前层命中**任一**锚点就返回。
所以在 `packages/foo/`（有 `package.json`、无 `.git`）里跑，返回的是 `packages/foo`。
后果：图谱只扫这个子包，跨包的引用看不见，`impact` 会少报影响面。
**少报影响面是最坏的错误方向** —— 模型会把"没有调用者"当事实去删代码。

`package.json` 当锚点本身是对的（非 git 目录也得能用），问题在于**优先级没生效**：
`.git` 排在第一位只影响"同一层里先看哪个"，不影响"哪一层胜出"。

**② 多根工作区被当成一个大仓。** cwd 是父目录时：

- 父目录通常没有锚点 → `findRepoRoot` 要么爬到更上层某个碰巧有 `package.json` 的目录，
  要么一路找不到、返回起点本身（`paths.ts:52`）
- 图谱从这个"根"往下扫，把两个仓的文件混进**同一张图**
- `readHeadSha`（`src/graph/graph-report.ts`）读 `<root>/.git/HEAD` → 拿不到 →
  缓存失效判据只剩 mtime 与文件数（`src/runtime/graph-cache.ts:101`），切分支不再触发重建
- 配置只认父目录那份 `.codebuddy/`，**各子仓自己的 redlines.json 全部被忽略**

第三条最危险：人在各仓里写好的红线，插件一条都不读，而界面上没有任何异常。

### 1.4 已经修掉的一处：会话状态跨仓撞 key

会话状态放在 `$HOME/.repo-guard/`（原因见 `paths.ts` 顶部：写进仓库会污染 `git status`），
而它的 key 曾经是**裸的仓库相对路径**。两个仓都有 `src/components/Existing/index.tsx` 时：
在 A 仓查过影响面，写 B 仓那个同名文件**就被放行**。

守卫方向性地从"多拦"变成"漏拦"，而这个方向的失败是不可接受的。

现在凡是 key 里含路径、或含"本仓知识"的状态，一律走 `scopePrefix(repoDir)`
（`src/runtime/session-state.ts`），由 `repoId()`（`paths.ts`，realpath 归一 + FNV-1a 短 hash）
提供稳定标识。回归用例 **G3**（`bin/verify-hooks.mjs`）钉住这条：
把仓前缀去掉，G3 立刻从 deny 变 allow。

**函数签名本身就是这份划分的文档：带 `repoDir` 参数的是仓级状态，不带的是会话级。**

| 会话级（不带 repoDir） | 为什么 |
|---|---|
| `toolCalls` / `consecutiveFail` / `repeatCount` | 回答"这个 agent 这一轮的行为"。按仓拆开会让每个仓各自从 0 数起，L3 循环门直接失效 |
| `countSessionFiles` | 范围预算管的是"这次任务涉及面有多宽"。跨仓各改 4 个文件，涉及面就是 8 个 |
| `evidence` / `stopNotices` | 见 5.1，这两个的多仓语义待定 |

## 2. 演进的支点：仓由文件决定，不由 cwd 决定

这是整个演进唯一的关键语义反转。

现在是 `repoOf(input)` → 一个仓 → 判所有文件。
多仓下必须反过来：`resolveRepoFor(filePath)` → 这个文件属于哪个仓 → 用**那个仓**的配置与图谱判。

`toRepoRelative` 已经会对仓外路径返回 `null`，把这个 `null` 的处理从"放行"改成
"换下一个仓再试"，就是路由的雏形。

### 2.1 要动的位置

| 位置 | 现在 | 多仓下 |
|---|---|---|
| `paths.ts:38` `findRepoRoot` | 返回单个根 | 增一个 `discoverRepos(workspaceDir)`：扫一层子目录找 `.git`，返回仓列表 |
| `paths.ts` | — | 增 `resolveRepoFor(repos, filePath)`：按最长前缀匹配定仓 |
| `hooks/index.ts:131` | `repoOf(input)` | 写类事件先定仓再判；一次事件涉及多个仓时按仓分组 |
| `runtime/graph-cache.ts` | `getGraph(repoDir)` | 不变，但调用方变成"只给本次涉及的仓建图"。**绝不能 N 个仓一起建** —— `pre-write` 只有十几秒预算 |
| `gates/config.ts`、`runtime/redlines.ts` | 只读 `<repo>/.codebuddy/` | 增工作区级共享层 `<workspace>/.codebuddy/`，各仓覆盖 |
| `session-state.ts` | 已按仓限定（1.4） | 不用再改 |

### 2.2 为什么会话状态用显式参数，而不是进程级的"当前仓"

用一个 ambient 全局（像 `setSessionId` 那样）能少改十几个签名，但那等于把
"一个进程只服务一个仓"钉进状态层 —— 而多仓的第一步恰恰是要拆掉这个假设。
到那时 ambient 值得在每个文件判定前重设一次，是最容易漏的那种写法。

### 2.3 顺手要修的两件事

- **`findRepoRoot` 的锚点优先级**：改成"先在所有层里找 `.git`，找不到再退回其他锚点"，
  修掉 1.3① 的子包截断。这件事**与多仓无关也该做**，monorepo 现在就受影响。
- **多根工作区的显式警告**：`session-start` 时如果发现根下有多个子目录含 `.git`，
  必须明说"检测到多个仓库，当前只守 X"。1.3② 最坏的地方是它完全沉默。

## 3. 本地图谱 vs 服务端图谱

### 3.1 分水岭是"未提交的改动"

| | 本地（现在） | 服务端 |
|---|---|---|
| 图谱的输入 | **工作区当前状态**，含未提交改动 | **(repo, commit)** 二元组 |
| 失效判据 | HEAD sha + 源文件最大 mtime（`graph-cache.ts:101`） | commit 变了重新索引 |
| 分支是维度吗 | **不是**。只有一个"现在"，切分支自动失效重建 | 是，而且是爆炸性的 |
| 未提交的改动 | 进图（第二条 mtime 判据专门管这个） | **结构性拿不到** |
| 建图成本 | 每仓一次全量，万文件级几十秒；所以 hook 只读缓存、永不建图 | 集中算，客户端零成本 |

`graph-cache.ts:12-14` 那段注释把要害写死了：AI 刚改完还没提交时，图谱不跟着更新，
`impact` 给的就是旧答案，而"给旧答案比不给答案更坏 —— 人会信它"。
服务端在这个点上不是工程量问题，是拿不到数据。

### 3.2 多分支为什么是服务端侧的真问题

服务端要为谁建图？三条路都不通：

- **只建默认分支** → 开发者在 feature 分支上，图谱和他手上的代码差 N 个 commit
- **每个活跃分支都建** → N 仓 × M 分支，而且 feature 分支生命周期短、建完就废
- **按需建**（收到查询才建那个 commit） → 首次查询几十秒，而 `pre-write` 只有十几秒预算

### 3.3 把两类仓分开，M 这个维度就塌成 1

| | 手上正在改的仓 | 被影响的对方仓 |
|---|---|---|
| 需要什么 | 符号级图谱 + 未提交改动 | 只需要"我这个 handler 谁在调" |
| 相关状态 | 唯一的"现在" | 已合入/已部署的那个 commit |
| 分支维度 | 不存在（只有一个现在） | 默认分支就够 —— 线上跑的就是那个 |
| 本地要有代码吗 | 必须有 | 不必，甚至可能没 clone |
| 结论 | **本地实时图谱，不可替代** | 预建索引完全够，甚至更好 |

所以本地与服务端不是二选一，是**分工**。

## 4. 跨仓影响面：契约索引，不是合并图谱

### 4.1 微服务的跨仓边是契约边

后端微服务之间不共享符号，耦合全在 HTTP / RPC / MQ topic 上。
所以跨仓**不需要合并图谱**，只需要一张契约索引：谁提供 `POST /order/create`、谁在调它。

数据量差两三个数量级 —— 一个仓几百条路由，不是几万个符号。小到可以进 git。

### 4.2 现有基建盘点

两端**已经在说同一种语言**，这是最省的地方：

| 侧 | 现有产出 | 出处 |
|---|---|---|
| provider | `RouteNode { method, urlPath, handlerFile, handlerFn }` | `graph/types.ts:117`，由 `go-gin.ts` / `java-spring.ts` / `python-ast.ts` 产出 |
| consumer（前端） | `calls[]` 里 `toObj='@api'`、`toMethod='POST /console/xxx'` | `web-frontend.ts:31`、`:806`、`:1018` |
| consumer 字段级 | `ApiContract { api, request[], response[], callSiteCount }` | `graph/types.ts:179`、`frontend-contracts.ts:53` |
| URL 归一 | 去 method 前缀、去首尾斜杠、大小写无关 | `cli/trace.ts:28-42` |

join key 现成：consumer 侧的 `toMethod` 和 provider 侧的 `method + urlPath` 是同一形态。

**缺的那一块是后端→后端**：`go-gin.ts` / `java-spring.ts` / `python-ast.ts` 都**不产出 `@api` 出向边**
（grep `@api` 在这三个文件里零命中），也就是"这个 Go 服务调了别的服务的哪个接口"识别不出来。
微服务之间的依赖恰恰是这一类，所以这是跨仓能力的**第一个必做项**，
不是"合并图谱"那种大工程。

### 4.3 一个必须继承的教训

`cli/trace.ts:1-20` 记着一个坑：engine 的 `findRoute` 在精确匹配失败后会拿**末段**去撞，
于是前端仓查 `/api/users` 会命中页面路由 `PAGE /users`，然后一本正经输出那个页面的调用链。
**跨仓 join 只允许严格匹配。** 跨仓场景下同名末段的概率比单仓高得多，
而这里给错答案比给不出答案坏得多。

### 4.4 三级落地（渐进，不互斥）

1. **对方仓也在工作区** → 插件自己扫，零依赖。2–5 个仓的场景够用
2. **对方仓不在本地** → 消费对方仓库里提交的 `.codebuddy/contracts.json`（由对方 CI 产出），
   通过 git 分发。**仍然零服务端**，而且和红线一样是"意图跟着代码走 PR、能 review、能回溯"，
   完全贴合 DESIGN.md 5.2 那条纪律
3. **仓太多** → 才需要服务端聚合契约索引。注意这时服务端**只存契约不存图谱**，
   所以第 3.2 节的多分支问题根本不存在（只索引默认分支）

第 2 级是性价比最高的一档：拿到跨仓能力、没破零服务端定位、也不用面对多分支建设。

## 5. 待定项与不做的事

### 5.1 语义待定

- **`evidence`（L5 工程校验证据）**：现在是会话级。A 仓跑了 test 不代表 B 仓验过，
  严格说该按仓记。暂不改的理由：L5 默认关、开启后也只提醒（`gates/delivery.ts:4-7`），
  风险低于改动成本。多仓真正落地时要重新判。
- **`repeatCount`（L3 重复调用）**：指纹含路径但不带仓，多仓下两个仓的同名文件会合并计数，
  于是循环门**更早**触发。"反复在同一个相对路径上打转"本身就是卡住的信号，
  这个方向偏严，是安全的，故意保留。
- **交付瘦身的文件数**：用跨仓总数。一次提交横跨多个仓时（微服务改动常常如此），
  管的仍然是"这个提交塞了多少东西"。

### 5.2 不做

- **不做跨仓的符号级图谱合并。** 那是服务端的活，而且对微服务场景没有必要（4.1）。
- **不做 git submodule 的特殊处理。** submodule 就是嵌套仓库，用 2.1 的仓列表机制统一处理。
- **不为多仓引入数据库或常驻进程。** 零服务端是这个插件的定位，不是权宜之计。

# 00 门禁索引

> 本文件是模型侧可见的**唯一**门禁信息，共 7 条。
> 只列 ID、意图与实现途径。检查项、判定方式、阈值、工具、命令留在 `gates/`，不进上下文。

## 门禁与规范：互补，不重叠

| | 门禁 | 规范（01~12 维） |
|---|---|---|
| 是什么 | 流水线或既有平台执行的机械检查 | 需要理解语义、权衡取舍的要求 |
| 谁判定 | 工具与平台 | 人与模型自查 |
| 你做什么 | **只读取结论** | **逐条自查并留证据** |
| 结论形态 | 通过 / 不通过 | 已达成 / 未达成 / 未验证 / 不适用 |

⛔ **同一要求不会同时出现在两侧**。规范正文中不出现门禁 ID。

**这意味着**：规范里的每一条「必须」，都是**机器帮不了你**的。不要指望流水线兜底。

## 门禁清单

| ID | 意图 | 实现途径 |
|---|---|---|
| G-01 | 构建成功、无告警，且依赖锁定与声明一致 | 流水线 |
| G-02 | 测试用例全部通过、并发竞态检测通过、覆盖率达阈值 | 流水线 |
| G-03 | 格式化零差异、静态检查规则集零告警 | 流水线 |
| G-04 | 单次变更规模、新增重复代码、新增未引用代码与新增依赖数均不超上限 | 流水线 |
| G-05 | 无凭据泄露，且静态应用安全检测无高危问题 | 安全扫描平台 |
| G-06 | 依赖无高危漏洞、许可证合规，且物料清单已产出 | 安全扫描平台 |
| G-07 | 分支与提交符合规范、有独立评审人、门禁未通过不得合入、受保护分支历史未改写 | 代码托管平台规则 |

**所有门禁均为阻断级**：不通过即不可交付。

## 怎么用

| 场景 | 处置 |
|---|---|
| 交付前 | 规范侧逐条自查；门禁侧等待流水线与平台结论 |
| 门禁未通过 | 按报告修复源头问题。⛔ 禁止修改判据、调阈值、加抑制、加跳过参数 |
| 想知道某门禁的阈值或具体检查项 | 不可知，也不需要知道 |
| 门禁结论尚未取得 | **视为未通过**。⛔ 禁止预测结论 |
| 某门禁不适用 | 显式登记「不适用 + 原因」，禁止静默省略 |
| G-04 超限且理由正当 | 走显式豁免登记，注明理由与确认人。⛔ 不得调低阈值放行 |

## G-04 的能力边界

G-04 针对 AI 生成代码的典型失效模式：产出体量远超必要、不检索既有实现而重新造一遍、顺手引入新依赖、留下未被调用的代码。

⚠️ **它只能测量体量，测不出「这段抽象是否必要」**。语义侧的判断在 `15-ai-execution-discipline` §九与 `01-coding-baseline`，二者缺一不可：

- 体量不超标 **不等于** 没有过度设计——五十行的多余抽象照样过门禁
- ⛔ 不得以 G-04 通过为由跳过 12 维 §九的自查

## 为什么只有 7 条

准入判据四条，缺一不可：

| 判据 | 含义 |
|---|---|
| **输入确定** | 检测对象是仓库内文件或流水线产物，不依赖外部事实库 |
| **算法确定** | 同一输入永远同一结论，不需要理解语义、不需要人工复核 |
| **工具通行** | 已有成熟工具或平台能力可承载，不需要自研检测器 |
| **结论二值** | 通过 / 不通过，无中间态、无「疑似」、无「建议人工确认」 |

不满足者一律留在规范侧。举例：

- 「非生产环境配置不指向生产资源」——须先有权威的**生产资源清单**才能判定，扫描器见到一个地址串无从判断其归属 → 违反输入确定 → 归 `08-config-environment`
- 「超时不倒挂」——须掌握跨服务调用拓扑与超时预算，且须区分串行与并行 → 违反输入确定与算法确定 → 归 `06-resilience`
- 「日志无敏感字段」——静态扫描只覆盖字面量，对变量拼接无效 → 违反算法确定 → 归 `07-observability` 与 `14-security-baseline`
- 「过度抽象检测」——须理解设计意图与演进预期，可机械测量的只有体量 → 违反算法确定 → 体量归 G-04，语义归 `01-coding-baseline` 与 `15-ai-execution-discipline`

> **一条容易被违反的纪律**：不要因为某项要求「看起来可以写个脚本扫一下」就认为它有门禁兜底。**能扫出一部分**与**能机械判定**是两回事，前者的漏报比不检查更危险——它会让人以为已经查过了。

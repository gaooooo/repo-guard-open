# 03 变更纪律与兼容性

> 覆盖最小改动与可追溯、语义化版本、接口兼容红线、数据兼容、配置兼容、废弃与下线。
> **本维度定义「兼容性三向」「破坏性变更」「废弃流程」三个概念，其余维度引用不重述。**

## 概念定义

| 概念 | 定义 |
|---|---|
| **兼容性三向** | 任一变更须同时评估三个方向：**向后兼容**（新版本能处理旧调用方与旧数据）、**向前兼容**（旧版本能处理新产生的数据与配置）、**双向共存**（新旧版本并行运行期间互不破坏）。滚动发布与灰度期间三者同时成立才可发布 |
| **破坏性变更** | 使既有调用方、既有数据或既有配置在不修改的前提下无法继续正常工作的变更 |
| **废弃流程** | 四阶段：标记废弃 → 公告与观察期 → 新旧双轨 → 下线。任一阶段缺失即不构成合规下线 |

## 一、最小改动与可追溯

### 必须

- **`必须[H]`** 每处改动必须可追溯到明确的需求条目或缺陷条目。**违反的表现**：交付中混入无人要求的改动，评审者无法判断其必要性
- **`必须[H]`** 变更范围必须限定在需求所需的最小集合，能改一处不改十处。**违反的表现**：为实现一个小功能顺带重写整个模块，风险面失控
- **`必须[H]`** 禁止在功能变更中夹带无关重构。重构须作为独立变更单独提交。**违反的表现**：功能改动淹没在大量格式与结构调整中，评审失效，回滚时无法只回滚功能部分
- **`必须[H]`** 不得擅自改动相邻的注释、格式、命名与代码结构。**违反的表现**：变更比对中真实改动占比极低，评审成本成倍上升
- **`必须[H]`** 发现与本次变更无关的问题代码时，记录并上报，不在本次变更中修改。**违反的表现**：顺手修复引入新缺陷，且不在本次验证范围内
- **`必须[H]`** 仅清理因本次改动产生的无引用代码；既有无引用代码只记录不删除。**违反的表现**：删除了实际被外部反射或配置引用的代码，运行期才暴露
- **`必须[H]`** 变更必须附影响面清单，覆盖接口、配置、数据结构、下游依赖四类。**违反的表现**：下游在无通知情况下被破坏

### 推荐

- 大变更拆分为多个可独立验证、可独立回滚的小变更
- 重构与功能变更在提交历史上明确区分，便于按类型回溯
- 影响面清单随变更演进持续更新，而非仅在开始时编写一次

## 二、版本与变更分级

### 必须

- **`必须[H]`** 对外交付物必须有版本标识，版本号语义明确且单调。**违反的表现**：调用方无法表达依赖关系，问题无法定位到具体版本
- **`必须[H]`** 破坏性变更必须升主版本，且不得以次版本或修订版本形式发布。**违反的表现**：调用方按兼容规则自动升级后直接失败
- **`必须[H]`** 每次变更必须判定是否构成破坏性变更，并记录判定结论与依据。**违反的表现**：破坏性变更被当作普通变更发布
- **`必须[H]`** 版本一经发布其内容不得变更；修正须发布新版本。**违反的表现**：同一版本号在不同时间内容不同，问题无法复现

### 推荐

- 破坏性变更集中在少数版本发布，避免频繁打断调用方
- 版本发布附变更说明，区分新增、变更、废弃、移除四类
- 提供版本支持周期说明，明确各版本的维护截止点

## 三、接口兼容

### 必须

- **`必须[H]`** 已发布接口的字段只增不删；字段标识与类型不得变更；字段语义不得变更。接口契约定义见 `04-api-contract`。**违反的表现**：调用方按旧语义解析新数据，产生错误业务结果
- **`必须[H]`** 新增字段必须为可选，且缺失时行为与变更前一致。**违反的表现**：旧调用方未提供新字段直接被拒绝
- **`必须[H]`** 不得收紧既有入参的校验规则（值域缩小、可选改必填、枚举减少）。**违反的表现**：调用方原本合法的请求突然被拒
- **`必须[H]`** 不得扩张既有出参的取值范围（新增枚举值、扩大值域），除非调用方已确认能处理未知取值。**违反的表现**：调用方遇到未知枚举值时异常终止
- **`必须[H]`** 不得变更既有错误码的语义，不得改变既有错误场景返回的错误码。**违反的表现**：调用方的错误处理分支全部失效
- **`必须[H]`** 接口行为变更（时序、幂等性、副作用、一致性保证）与定义变更同等对待，须走同样的兼容性评估。**违反的表现**：接口定义未变但行为已变，机械检测无法发现，调用方在生产中才发现
- **`必须[H]`** 破坏性接口变更必须通过新增接口实现，不得原地修改。**违反的表现**：无法提供新旧共存期，调用方被迫同步升级

### 推荐

- 接口变更前确认全部调用方，评估逐一升级成本
- 未知字段与未知枚举值的处理策略在契约中显式约定
- 新增接口与既有接口在命名上可区分版本

## 四、数据兼容

### 必须

- **`必须[H]`** 数据结构变更必须满足双向共存：变更期间新旧版本代码同时运行且均能正常读写。**违反的表现**：滚动发布过程中新旧实例互相破坏数据
- **`必须[H]`** 新增字段必须可空或带默认值，存量数据不迁移即可正常读取。**违反的表现**：新代码读取存量数据时因字段缺失而失败
- **`必须[H]`** 字段删除与重命名必须走废弃流程，不得一步到位。**违反的表现**：尚未升级的实例读写已删除字段直接失败
- **`必须[H]`** 结构变更与数据迁移必须拆分为独立步骤，每步可独立回滚。**违反的表现**：迁移中途失败，数据处于新旧混合的不一致状态
- **`必须[H]`** 每个迁移必须有对应的回退方案，且回退方案在执行前已验证可用。数据操作规范见 `09-data-storage`。**违反的表现**：迁移出错后无法恢复
- **`必须[H]`** 迁移必须可重入：重复执行结果一致，不产生重复数据或二次修改。**违反的表现**：中断后重试导致数据被处理两次

### 推荐

- 大规模迁移分批执行，每批后校验并可中止
- 迁移期间新旧字段双写，确认一致后再切换读取来源
- 迁移前留存可恢复的数据快照

## 五、配置兼容

### 必须

- **`必须[H]`** 新增配置项必须有默认值，旧配置在新代码下可正常运行。配置管理规范见 `08-config-environment`。**违反的表现**：新代码要求新配置项，未更新配置的环境启动失败
- **`必须[H]`** 不得变更既有配置项的语义、单位与默认值。需要变更时新增配置项并废弃旧项。**违反的表现**：配置值未变但行为已变，无人察觉
- **`必须[H]`** 配置向前兼容必须成立：新配置能被旧版本代码正常加载，使代码可独立回滚。**违反的表现**：回滚代码后旧版本无法解析新配置，被迫同时回滚配置
- **`必须[H]`** 配置项删除必须走废弃流程，且下线前确认无环境仍在使用。**违反的表现**：删除后某环境配置校验失败

### 推荐

- 新配置项默认值按「保持变更前行为」选取
- 配置项变更在变更说明中单列，与代码变更同等对待

- 配置项变更兼容性核对表 → `examples/`

## 六、废弃与下线

### 必须

- **`必须[H]`** 任何对外能力的移除必须走完整废弃流程：标记废弃、公告与观察期、新旧双轨、下线。**违反的表现**：能力直接消失，调用方在生产中才发现
- **`必须[H]`** 废弃标记必须在定义处可见，且调用方在使用时能够感知。**违反的表现**：废弃信息只写在文档中，调用方持续新增使用
- **`必须[H]`** 公告必须送达全部已知调用方，并给出替代方案与截止时间。**违反的表现**：公告只发布在无人阅读的位置，等同未通知
- **`必须[H]`** 下线前必须确认无实际调用。无法确认调用情况时不得下线。**违反的表现**：凭猜测下线，影响未知调用方
- **`必须[H]`** 下线后必须保留可快速恢复的手段，直至确认无影响。**违反的表现**：下线引发故障后无法快速恢复
- **`必须[H]`** 废弃期间旧能力必须保持可用，不得降低其可靠性以促使调用方迁移。**违反的表现**：以变相劣化迫使迁移，引发不可预期故障

### 推荐

- 废弃标记中注明替代方案与预计下线时间
- 通过调用统计确认迁移进度，而非依赖调用方自述
- 下线分阶段执行，先限流再停用最后移除

- 废弃流程四阶段模板与公告模板 → `examples/`

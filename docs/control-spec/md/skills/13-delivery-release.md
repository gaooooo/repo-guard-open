# 13 交付与发布

> 覆盖分支与提交、评审判据、可复现构建、制品与镜像、版本与可追溯、发布策略、可回滚性与开关。
> **本维度定义「可追溯链」「可回滚性」「发布单元」三个概念，其余维度引用不重述。**

## 概念定义

| 概念 | 定义 |
|---|---|
| **可追溯链** | 由「运行实例 → 制品 → 提交 → 变更记录 → 需求条目」构成的完整链条。任一环断裂，故障复盘即无法还原当时状态 |
| **可回滚性** | 变更能否在不依赖额外开发的前提下退回变更前状态。**这是变更前必须具备的设计属性，不是出问题后才考虑的补救手段** |
| **发布单元** | 一次发布中必须整体生效或整体回退的内容集合，可能同时包含制品、配置与数据结构。**跨载体的关联变更属于同一发布单元** |

---

## 一、分支与提交

### 必须

- **`必须[H]`** 每个提交必须是一个完整且自洽的逻辑单元，不得提交半成品状态。**违反的表现**：任意提交点都无法构建，二分定位失效
- **`必须[H]`** 提交信息必须说明变更内容与原因，不得只写一个动词或文件名。**违反的表现**：历史记录无信息量，回溯只能逐个查看差异
- **`必须[H]`** 提交必须可关联到需求或缺陷条目。可追溯要求见 `03-change-compatibility`。**违反的表现**：无法回答「这行代码为什么存在」
- **`必须[H]`** 禁止改写已共享的提交历史，禁止强制推送至受保护分支。**违反的表现**：他人本地状态与远端不一致，工作丢失
- **`必须[H]`** 禁止提交构建产物、依赖副本、本地配置与临时文件。配置要求见 `08-config-environment`。**违反的表现**：仓库膨胀，且本地配置中的凭据随之扩散
- **`必须[H]`** 分支生命周期必须受控，合入后及时清理，长期分支须说明理由。**违反的表现**：长期分支与主干差异过大，合入时冲突不可控

### 推荐

- 分支存活周期短，尽早合入以减少偏离
- 提交粒度与评审粒度匹配，便于逐个提交评审
- 提交信息格式统一，便于自动化提取

### 参考

- 分支模型与提交信息模板 → `examples/`

## 二、评审

### 必须

- **`必须[H]`** 合入主干是人工决策点，不得完全自动化。**违反的表现**：无人对合入结果负责
- **`必须[H]`** 变更说明必须包含变更内容、影响面清单与验证证据位置，不得留空或仅引用标题。验证证据要求见 `11-quality-testing`。**违反的表现**：评审者缺乏判断依据，评审退化为形式
- **`必须[H]`** 评审必须覆盖非代码类改动：配置、数据结构、构建定义、部署定义。**违反的表现**：高风险配置改动无人审查
- **`必须[H]`** 评审意见必须处置完毕方可合入：接受并修改，或说明不接受的理由。**违反的表现**：意见被忽略，同类问题反复出现
- **`必须[H]`** 禁止通过修改门禁判据、调整阈值、添加抑制或跳过参数来使门禁通过。**违反的表现**：门禁形同虚设，问题被带入生产
- **`必须[H]`** 变更规模必须控制在可被有效评审的范围内，超限须拆分。**违反的表现**：超大变更无法被真正审查，评审只剩签字
- **`必须[H]`** 自动化评审结论不得替代人工判断，尤其对其覆盖不到的改动类型。**违反的表现**：自动评审通过即合入，而其恰好不覆盖本次改动

### 推荐

- 评审关注点分层：正确性与兼容性优先，风格问题交由自动化
- 高风险变更指定熟悉该领域的评审人
- 评审中发现的共性问题沉淀为规则或门禁

- 变更说明模板与评审关注点清单 → `examples/`

## 三、构建与依赖

### 必须

- **`必须[H]`** 构建必须可复现：同一来源标识在不同时间、不同机器上构建出内容一致的产物。**违反的表现**：线上产物无法从源码重新构建出来，问题无法复现
- **`必须[H]`** 构建必须有唯一入口，本地构建与流水线构建使用同一套定义。**违反的表现**：本地通过而流水线失败，或反之
- **`必须[H]`** 构建过程不得依赖执行机器的本地状态与人工干预。**违反的表现**：换机器即失败，构建不可重复
- **`必须[H]`** 依赖必须锁定到确定版本，禁止使用浮动版本。**违反的表现**：同一提交在不同时间构建出不同产物
- **`必须[H]`** 引入新依赖必须评估其维护状态、许可证与安全记录，并记录引入理由。供应链要求见 `14-security-baseline`。**违反的表现**：引入无人维护或许可证不合规的依赖
- **`必须[H]`** 构建必须在受控环境执行，不得使用个人环境产物作为交付物。**违反的表现**：交付物内容无法追溯与复现

### 推荐

- 构建缓存不影响结果确定性，可随时清空重建
- 依赖更新定期进行，避免长期滞后后一次性大升级
- 构建耗时纳入观测，异常增长及时处理

### 参考

- 构建入口定义与依赖引入评估清单 → `examples/`

## 四、制品与可追溯

### 必须

- **`必须[H]`** 构建环境与运行环境必须职责分离，不得把构建工具链带入运行产物。**违反的表现**：运行环境携带编译器与源码，攻击面成倍扩大
- **`必须[H]`** 构建上下文必须最小化，制品不得包含与运行无关的内容。**违反的表现**：制品体积失控，分发与启动变慢
- **`必须[H]`** 变更必须与制品版本、配置版本三者关联可追溯。**违反的表现**：故障复盘无法还原当时运行的代码与配置组合
- **`必须[H]`** 制品必须不可变：一经产出其内容不得修改，修正须产出新制品。**违反的表现**：同一标识的制品内容不同，问题无法复现
- **`必须[H]`** 制品所依赖的基础环境必须固定到确定版本，禁止使用随时间变化的浮动标识。**违反的表现**：同一份定义在不同时间产出行为不同的制品，问题无法复现
- **`必须[H]`** 制品标识必须可反查来源提交与构建记录。**违反的表现**：线上运行的代码版本无法确定
- **`必须[H]`** 运行实例必须能自证其制品版本。**违反的表现**：故障时无法确认实例运行的是哪个版本
- **`必须[H]`** 制品不得包含凭据、内部地址与非必要文件。安全要求见 `14-security-baseline`。**违反的表现**：凭据随制品分发
- **`必须[H]`** 制品必须以非特权身份运行，不得使用最高权限。**违反的表现**：一处漏洞即导致运行环境完全失守
- **`必须[H]`** 可追溯链必须完整，任一环断裂须在交付前补齐。**违反的表现**：复盘时无法还原当时的代码、配置与变更原因

### 推荐

- 制品与配置版本的对应关系集中记录
- 制品保留期覆盖可能的回滚窗口
- 运行时暴露版本信息的统一查询方式

### 参考

- 制品标识规范与可追溯链核对表 → `examples/`

## 五、发布与灰度

### 必须

- **`必须[H]`** 发布必须灰度进行，禁止一次性全量替换。**违反的表现**：缺陷瞬间影响全部流量
- **`必须[H]`** 发布单元必须完整识别：制品、配置、数据结构中相互依赖的部分须同批发布或明确先后次序。**违反的表现**：代码已发布而配置未同步，运行时报错
- **`必须[H]`** 发布必须定义推进判据与中止判据，达到中止判据须立即停止。**违反的表现**：异常已出现但发布继续推进
- **`必须[H]`** 灰度期间必须观测关键指标，观测项在发布前即确定。可观测要求见 `07-observability`。**违反的表现**：灰度期间无人观测，等同于直接全量
- **`必须[H]`** 发布过程不得中断在途请求。优雅上下线要求见 `05-discovery-routing`。**违反的表现**：每次发布产生一批失败请求
- **`必须[H]`** 存在依赖关系的多个服务发布时，次序必须按兼容性确定并显式声明。兼容性要求见 `03-change-compatibility`。**违反的表现**：下游先于上游发布，接口不匹配
- **`必须[H]`** 发布必须留下记录：发布内容、时间、执行人、结果。**违反的表现**：故障时无法判断是否与发布相关

### 推荐

- 灰度批次按可控维度划分，从影响最小的范围开始
- 每批次之间留观测窗口，不连续推进
- 高风险发布避开业务高峰并提前告知相关方

## 六、可回滚性与开关

### 必须

- **`必须[H]`** 每次变更在发布前必须具备回滚方案，且方案已确认可执行。**违反的表现**：出问题后才发现无法回滚
- **`必须[H]`** 回滚不得依赖额外开发，必须使用既有制品与既有配置版本。**违反的表现**：回滚需要临时改代码，耗时远超预期
- **`必须[H]`** 不可回滚的变更（数据结构破坏性变更、外部不可逆操作）必须事先识别并单独评估，不得混入常规发布。**违反的表现**：以为可回滚，执行时才发现数据已不可逆
- **`必须[H]`** 配置向前兼容是代码独立回滚的前提，必须在发布前确认成立。配置兼容要求见 `08-config-environment`。**违反的表现**：回滚代码后旧版本无法解析新配置
- **`必须[H]`** 新功能必须带开关且默认关闭，开关可独立于发布进行切换。**违反的表现**：功能出问题只能整体回滚，影响同批次其他变更
- **`必须[H]`** 开关必须可快速关闭，关闭路径在启用前已验证。**违反的表现**：故障时无法及时止损
- **`必须[H]`** 开关的清理责任必须明确：功能稳定后移除开关与旧分支代码。**违反的表现**：开关长期堆积，代码分支组合爆炸且无人敢清理
- **`必须[H]`** 回滚后必须确认系统实际恢复至预期状态，不得仅以执行完成为准。**违反的表现**：回滚动作完成但残留状态导致问题持续

### 推荐

- 回滚方案与发布方案一并评审
- 回滚能力定期演练验证
- 开关设置有效期，到期未清理即触发提醒

### 参考

- 回滚方案模板与开关生命周期管理 → `examples/`

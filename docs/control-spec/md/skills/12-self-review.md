# 12 自我评审

> 交付给他人评审**之前**，由产出方对自己的全部产出做一次完整审查。
> 覆盖通用要求、分形态检查（代码 / 配置 / 数据脚本 / 文档与方案 / 取数结果）、评审记录与遗留项。
> **本维度定义「自审」「换位视角」「自审记录」三个概念，其余维度引用不重述。**
>
> 分工：本维度管**交付前自己审自己**；他人评审的判据与流程归 `13-delivery-release`；
> 验证是否实际执行归 `11-quality-testing`；如实汇报归 `15-ai-execution-discipline`。

## 概念定义

| 概念 | 定义 |
|---|---|
| **自审** | 产出方在提交他人评审前，以评审者视角对自己产出做的完整审查。**它不是「再看一遍」，而是带着明确检查项逐条对照** |
| **换位视角** | 自审时必须切换的三种视角：**使用者**（会怎么用、会怎么误用）、**维护者**（半年后能否看懂、能否安全修改）、**攻击者**（哪里可被滥用）。只用作者视角看不出问题 |
| **自审记录** | 自审的产出物：检查了什么、发现并修复了什么、剩余哪些已知问题与理由。**无记录的自审等于未做** |

> **自审不能替代他人评审**。它的价值在于把低级问题拦在自己这一侧，使他人评审能聚焦于设计与业务正确性。

## 一、通用要求

### 必须

- **`必须[H]`** 全部产出在提交他人评审前必须完成自审，不限于代码。配置、数据脚本、文档、方案、取数结果同样适用。**违反的表现**：非代码产出无人自查，问题直达生产
- **`必须[H]`** 自审必须逐条对照检查项，不得以通读一遍代替。**违反的表现**：自审流于形式，同类问题反复出现
- **`必须[H]`** 自审必须在产出完成后、提交前进行，不得边写边算作自审。**违反的表现**：始终处于作者视角，看不出整体性问题
- **`必须[H]`** 自审必须覆盖本次变更的完整范围，与改动范围声明一致。范围声明见 `15-ai-execution-discipline`。**违反的表现**：只审主要改动，夹带的次要改动无人过目
- **`必须[H]`** 自审必须逐项核对本次适用的全部「必须」条目，不适用的显式标注原因。**违反的表现**：规范条目从未被真正对照，形同摆设
- **`必须[H]`** 自审必须以三种换位视角各过一遍，不得只从作者视角检查。**违反的表现**：只验证「按我的设想能跑通」，误用路径与维护成本完全未考虑
- **`必须[H]`** 自审发现的问题必须在提交前修复；确需保留的须显式登记为已知问题并说明理由。**违反的表现**：发现了却不改也不说，他人评审时重复发现
- **`必须[H]`** 自审不得依赖他人评审兜底。**违反的表现**：把未完成的产出丢给评审者，评审沦为代写
- **`必须[H]`** 产出为多人或多轮次协作结果时，自审须覆盖全部内容，不得只审自己新增的部分。**违反的表现**：拼接处的矛盾与重复无人发现

### 推荐

- 产出完成后先搁置片刻再自审，避免思维惯性
- 自审清单按产出形态预置，不每次临时回忆
- 反复出现的同类问题沉淀为检查项或规则集条目

- 自审清单模板与换位视角提问法 → `examples/`

## 二、代码自审

### 必须

- **`必须[H]`** 必须完整阅读一遍本次变更的全部差异，不得只检查记忆中改过的地方。**违反的表现**：误改、调试残留、无意提交的文件被带入
- **`必须[H]`** 必须确认每处改动都能追溯到需求条目，无法解释的改动予以删除。可追溯要求见 `03-change-compatibility`。**违反的表现**：交付了自己也说不清为何需要的代码
- **`必须[H]`** 必须逐条核对错误路径与边界条件，不得只验证正常路径。错误处理要求见 `02-error-handling`。**违反的表现**：正常流程正确但异常处理从未被检查
- **`必须[H]`** 必须确认新增逻辑有对应测试，且测试确实能感知逻辑变更。用例有效性见 `11-quality-testing`。**违反的表现**：测试存在但形同虚设
- **`必须[H]`** 必须确认无调试残留、无临时代码、无指向个人环境的内容。**违反的表现**：调试输出进入生产日志
- **`必须[H]`** 必须以攻击者视角检查输入处理与权限校验。安全要求见 `14-security-baseline`。**违反的表现**：只考虑正常输入，恶意输入路径完全未设防
- **`必须[H]`** 必须确认改动未破坏既有调用方与既有数据。兼容性要求见 `03-change-compatibility`。**违反的表现**：本次功能正确但打破了上下游
- **`必须[H]`** 必须确认产出规模与需求复杂度相称，可删减的部分予以删减。AI 生成代码的风险见 `15-ai-execution-discipline`。**违反的表现**：功能正确但体量数倍于必要

### 推荐

- 按差异逐文件审查，而非按记忆中的改动点
- 先审接口与数据结构，再审实现
- 对照相似的既有实现，确认风格与模式一致

- 代码自审清单与常见遗漏项 → `examples/`

## 三、配置自审

### 必须

- **`必须[H]`** 必须逐环境核对配置取值，不得只确认当前环境。环境隔离见 `08-config-environment`。**违反的表现**：一个环境正确而其余环境缺项或串用
- **`必须[H]`** 必须确认配置指向的资源与目标环境匹配，非生产不得指向生产。**违反的表现**：非生产操作作用于生产资源
- **`必须[H]`** 必须确认新增项有默认值、既有项语义未被改变。配置兼容见 `03-change-compatibility`。**违反的表现**：未更新配置的环境启动失败，或行为静默改变
- **`必须[H]`** 必须确认配置中无凭据明文、无未渲染占位符。**违反的表现**：凭据随配置扩散，或占位符被当作字面值使用
- **`必须[H]`** 必须确认配置变更的生效方式与预期一致，并确认生效可见性手段可用。生效可见性见 `08-config-environment`。**违反的表现**：以为热更新实际需重启，或已下发但未生效而双方均不知
- **`必须[H]`** 必须确认回滚路径可用：能回到变更前取值。**违反的表现**：出问题后只能手工回忆原值

### 推荐

- 变更前后取值逐项对照，而非只看新值
- 高风险配置项变更单独标注，提醒评审者重点关注

### 参考

- 配置自审清单与环境矩阵核对方法 → `examples/`

## 四、数据脚本自审

### 必须

- **`必须[H]`** 必须预估影响范围与影响行数，超出预期即停止并复查。写放大边界见 `09-data-storage`。**违反的表现**：预期改百行实际改百万行
- **`必须[H]`** 必须确认更新与删除带明确条件，无条件写一律不予提交。**违反的表现**：一次误操作影响全表
- **`必须[H]`** 必须确认逆向脚本存在、与正向配对且能真正还原。**违反的表现**：需要回退时才发现无法还原
- **`必须[H]`** 必须确认脚本可重入，重复执行不产生重复数据或二次修改。**违反的表现**：中断后重试导致数据被处理两次
- **`必须[H]`** 必须在与生产同构的环境实际执行验证，不得仅静态审读。验证要求见 `11-quality-testing`。**违反的表现**：脚本在生产首次执行，问题在生产暴露
- **`必须[H]`** 必须确认查询与变更带范围限定，不得全表扫描或全表改写。**违反的表现**：脚本执行期间锁表，业务大面积受影响
- **`必须[H]`** 必须确认执行前的数据状态可恢复，且恢复手段已确认可用。**违反的表现**：数据被错误改写且无法还原

### 推荐

- 先以只读查询确认待影响数据集，再执行变更
- 大规模变更分批设计，每批可校验、可中止
- 脚本附执行说明：预期影响、执行时机、校验方式、回退方式

### 参考

- 数据脚本自审清单与影响面预估方法 → `examples/`

## 五、文档与方案自审

### 必须

- **`必须[H]`** 必须确认文档中的事实性陈述有据可查，推断与假设显式标注。假设显式化见 `15-ai-execution-discipline`。**违反的表现**：推断被当作事实传递，下游据此决策
- **`必须[H]`** 必须确认文档与当前实现一致，不得保留已失效的描述。**违反的表现**：按文档操作失败，且文档错误比无文档危害更大
- **`必须[H]`** 必须以不具备背景知识的读者视角检查可理解性。**违反的表现**：只有作者看得懂，交接后无人能用
- **`必须[H]`** 方案必须确认关键决策有理由、有备选对比，不得只给结论。**违反的表现**：后人无法判断能否调整，方案变成不可动的黑盒
- **`必须[H]`** 方案必须确认影响面、验证方式与回退方式齐备，缺项即不得提交。**违反的表现**：方案看似完整但无法据以执行
- **`必须[H]`** 必须确认文档中无凭据、无内部敏感信息、无未脱敏数据。**违反的表现**：敏感信息随文档扩散至不受控范围
- **`必须[H]`** 必须确认文档内与文档间的引用有效、无自相矛盾。**违反的表现**：引用指向不存在的位置，或两处描述互相冲突

### 推荐

- 方案先给结论与影响面，再给论证过程
- 关键术语在文档内统一，与既有术语表一致
- 图示与正文保持同步，不保留过期图示

### 参考

- 方案自审清单与事实标注方式 → `examples/`

## 六、取数结果自审

### 必须

- **`必须[H]`** 必须确认口径与需求一致：时间范围、过滤条件、去重规则、统计维度逐项核对。**违反的表现**：数字本身无误但回答的不是所提的问题
- **`必须[H]`** 必须做量级合理性检查，数量级异常时先排查再交付。**违反的表现**：交付了明显异常的数字而未察觉
- **`必须[H]`** 必须确认数据源与时效符合要求，并说明数据截止时点。**违反的表现**：使用了过期或不完整的数据得出结论
- **`必须[H]`** 必须至少用一种独立方式交叉验证关键数字。**违反的表现**：单一路径的错误无从发现
- **`必须[H]`** 必须区分「值为零」与「无数据」，不得以零填充缺失。**违反的表现**：缺失被当作真实的零，结论完全错误
- **`必须[H]`** 交付内容必须遵循数据分级与最小化要求。数据分级见 `14-security-baseline`。**违反的表现**：超范围输出敏感字段
- **`必须[H]`** 必须随结果说明口径与已知局限，不得只给数字。**违反的表现**：使用方按自己的理解解读，得出与口径不符的结论

### 推荐

- 口径在取数前与需求方确认，而非事后解释
- 保留可重放的查询，使结果可被复核
- 异常值单独标注并给出可能原因

- 取数自审清单与口径确认模板 → `examples/`

## 七、自审记录与遗留项

### 必须

- **`必须[H]`** 自审必须留下记录：检查范围、发现的问题、修复情况、剩余已知问题。**违反的表现**：无从判断自审是否真正做过，也无法复核
- **`必须[H]`** 自审记录必须如实：未检查的项标注未检查，不得填为已通过。诚实标注见 `15-ai-execution-discipline`。**违反的表现**：记录完美而实际未审，比不记录危害更大
- **`必须[H]`** 已知问题必须逐项登记：问题描述、影响、不在本次修复的理由、后续处置。**违反的表现**：已知问题被遗忘，长期滞留无人跟进
- **`必须[H]`** 已知问题不得包含「必须」级条目的违反项。**违反的表现**：以登记代替修复，硬性要求被绕过
- **`必须[H]`** 自审记录必须随产出一并提交，作为他人评审的输入。**违反的表现**：评审者重复发现已被作者知晓的问题
- **`必须[H]`** 他人评审发现的问题必须回溯：判断本应在自审阶段被发现的，补充为检查项。**违反的表现**：同类问题在每次评审中反复出现

### 推荐

- 自审记录与符合性声明合并，避免两处填写
- 定期统计「他人评审发现但自审应能发现」的问题占比，据此改进检查项
- 检查项随踩坑经验持续补充，每项注明来由

### 参考

- 自审记录模板与已知问题登记表 → `examples/`

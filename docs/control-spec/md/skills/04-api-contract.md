# 04 接口契约

> 覆盖设计原则、协议选型、幂等性、错误码体系、分页与批量、契约文档与变更评审。
> **本维度定义「契约」「幂等键」「错误三分类」三个概念，其余维度引用不重述。**

## 概念定义

| 概念 | 定义 |
|---|---|
| **契约** | 调用方与被调方之间的完整约定：入参与出参结构、错误语义、幂等性、时序与副作用、规模上限、可用性承诺。**定义之外的实际行为不属于契约，调用方不得依赖** |
| **幂等键** | 由调用方生成、在约定时间窗内唯一标识一次业务操作的值。被调方据此保证重复请求只产生一次副作用 |
| **错误三分类** | 任一失败响应必须可归入且仅归入一类：**参数非法**（调用方错误，重试无意义）、**业务失败**（业务规则拒绝，重试无意义）、**系统故障**（被调方或其依赖异常，可能可重试） |

## 一、设计原则

### 必须

- **`必须[H]`** 接口必须表达业务意图而非内部实现结构。**违反的表现**：接口随内部重构而变更，调用方被内部实现绑架
- **`必须[H]`** 接口的副作用必须在契约中显式声明，不得存在未声明的副作用。**违反的表现**：调用方以为是查询，实际触发了状态变更
- **`必须[H]`** 读操作不得产生业务副作用。**违反的表现**：调用方为规避副作用而不敢重试查询
- **`必须[H]`** 单个接口职责单一，不得通过参数开关切换为语义完全不同的行为。**违反的表现**：一个接口承载多套语义，兼容性与权限控制均无法正确实施
- **`必须[H]`** 入参必须全量校验：类型、值域、长度、枚举、必填性、字段间约束。校验失败返回参数非法类错误。安全要求见 `14-security-baseline`。**违反的表现**：非法值进入业务逻辑，在深层引发不可解释的异常
- **`必须[H]`** 响应不得包含内部实现细节：内部错误堆栈、内部标识、内部地址、内部数据结构。**违反的表现**：内部信息外泄，且调用方开始依赖这些细节
- **`必须[H]`** 接口必须声明可用性与性能承诺（预期响应时间、规模上限），供调用方设定超时。超时要求见 `06-resilience`。**违反的表现**：调用方无依据设定超时，只能凭猜测

### 推荐

- 查询操作与命令操作分离，不在同一接口中混合
- 长耗时操作改为异步：提交返回受理凭证，另提供状态查询
- 字段命名在全部接口中保持一致，同一概念使用同一名称
- 可选字段的缺失语义在契约中明确，区分「未提供」与「显式置空」

## 二、协议与交互形态选型

### 必须

- **`必须[H]`** 协议与交互形态（同步调用、异步消息、流式、批量）的选择必须记录决策依据。**违反的表现**：选型无据可依，后续无人敢调整
- **`必须[H]`** 同一服务对外暴露多种协议时，各协议下的业务语义必须一致。**违反的表现**：同一操作经不同协议产生不同结果
- **`必须[H]`** 异步交互必须约定投递语义（至多一次、至少一次、恰好一次）与消费方的幂等要求。**违反的表现**：消息重复投递导致业务重复执行
- **`必须[H]`** 异步交互必须约定失败处置：重试策略、失败留存方式、人工介入入口。**违反的表现**：消息处理失败后静默丢弃，业务数据缺失且无人知晓
- **`必须[H]`** 流式与长连接交互必须约定连接生命周期、异常中断后的续传或重建方式。**违反的表现**：连接中断后数据缺失，双方均认为传输完成

### 推荐

- 内部调用与对外开放使用不同层次的接口，不直接暴露内部接口
- 交互形态选择优先满足一致性与可观测需求，其次考虑性能

## 三、幂等性

### 必须

- **`必须[H]`** 所有写操作必须定义幂等语义：要么天然幂等，要么由幂等键保证。**违反的表现**：调用方重试产生重复业务数据
- **`必须[H]`** 使用幂等键的接口必须声明幂等键的生成规则、唯一性范围与有效时间窗。**违反的表现**：调用方生成的键不满足唯一性，幂等失效
- **`必须[H]`** 幂等命中时必须返回与首次执行一致的结果，不得返回错误。**违反的表现**：调用方重试后收到冲突错误，无法判断首次是否成功
- **`必须[H]`** 幂等保证必须覆盖并发场景：同一幂等键的并发请求只产生一次副作用。**违反的表现**：并发重试绕过幂等检查，产生重复数据
- **`必须[H]`** 幂等窗口之外的重复请求行为必须在契约中声明。**违反的表现**：超窗重复请求被当作新请求执行，调用方无从预期
- **`必须[H]`** 结果未知（超时、连接中断）时调用方必须能确认操作是否已执行：或通过幂等重试，或通过状态查询接口。重试要求见 `06-resilience`。**违反的表现**：调用方既不敢重试也无法查询，业务卡死

### 推荐

- 幂等键由调用方生成，被调方不代为生成
- 提供操作结果查询接口，作为幂等重试之外的确认手段
- 幂等记录的保留期与业务重试窗口匹配

## 四、错误码体系

### 必须

- **`必须[H]`** 错误码必须全局唯一并登记在注册表中，新增错误码时同步更新。**违反的表现**：同一错误码在不同场景含义不同，调用方无法据此分支
- **`必须[H]`** 每个错误响应必须可归入错误三分类之一，调用方据此决定是否重试。**违反的表现**：调用方对确定性失败持续重试，放大故障
- **`必须[H]`** 错误码必须稳定：语义一经发布不得变更，既有错误场景返回的错误码不得改变。兼容性要求见 `03-change-compatibility`。**违反的表现**：调用方的错误处理分支全部失效
- **`必须[H]`** 错误响应必须包含可供人工定位的信息（错误码、可读描述、关联标识），且不泄漏内部细节。**违反的表现**：只有一个错误码，双方均无法定位具体问题
- **`必须[H]`** 传输层成功不得掩盖业务失败，失败必须通过明确的错误表达。**违反的表现**：失败以成功状态返回，调用方与监控均认为一切正常
- **`必须[H]`** 限流、熔断、降级引发的拒绝必须使用可识别的专用错误，区别于系统故障，并告知调用方可否重试。韧性要求见 `06-resilience`。**违反的表现**：被限流的调用方持续重试，加剧过载
- **`必须[H]`** 错误码不得承载业务数据，业务数据通过响应体表达。**违反的表现**：错误码空间被业务枚举占满，无法扩展

### 推荐

- 错误码分段规划，段位区分错误来源与类别
- 错误响应中区分「面向调用方的描述」与「面向排查的关联标识」
- 新增错误码时同步更新注册表与契约文档

## 五、分页与批量

### 必须

- **`必须[H]`** 所有可能返回多条结果的接口必须支持分页，不得返回不受限的全量结果。**违反的表现**：数据增长后单次响应过大，拖垮双方
- **`必须[H]`** 批量接口必须声明单次请求的规模上限，超限返回参数非法类错误。**违反的表现**：超大批量请求耗尽资源
- **`必须[H]`** 批量接口必须明确失败语义：整体失败还是部分失败。部分失败时必须逐项返回结果。**违反的表现**：调用方无法判断哪些成功哪些失败，重试导致部分重复
- **`必须[H]`** 批量操作的幂等性必须明确到单项粒度。**违反的表现**：整批重试导致已成功项被重复执行
- **`必须[H]`** 分页必须保证遍历过程的确定性：在数据变动情况下不产生重复项或遗漏项，或在契约中显式声明不保证。**违反的表现**：调用方遍历得到的数据集不完整且不自知

### 推荐

- 分页使用位置标记而非偏移量，避免数据变动导致错乱
- 返回总量为可选能力，避免为获取总量付出高昂代价
- 批量接口的规模上限作为配置项，可按环境调整

## 六、契约文档与变更评审

### 必须

- **`必须[H]`** 契约必须有单一权威定义源，文档与实现不得各自维护。**违反的表现**：文档与实现长期不一致，调用方按文档开发后失败
- **`必须[H]`** 契约文档与实现之间不得存在漂移；无法由单一源生成时，须在变更时人工核对二者一致。**违反的表现**：调用方按文档开发，集成时才发现实现不符
- **`必须[H]`** 契约必须完整覆盖：结构、错误语义、幂等性、副作用、规模上限、可用性承诺。缺项即视为契约不完整。**违反的表现**：调用方对未定义部分各自假设，行为不可预期
- **`必须[H]`** 契约变更必须经评审，评审须包含调用方视角的兼容性判定。**违反的表现**：变更单方面决定，下游被动承受
- **`必须[H]`** 契约变更必须通知全部已知调用方，通知须在变更生效前送达。**违反的表现**：调用方在故障中才发现契约已变
- **`必须[H]`** 契约测试必须覆盖错误分支与边界条件，不得只覆盖正常路径。测试要求见 `11-quality-testing`。**违反的表现**：正常路径正确但错误处理与契约不符

### 推荐

- 契约定义先于实现，以契约驱动双方并行开发
- 契约变更记录可追溯，能查询任一时点的契约内容
- 调用方清单持续维护，作为变更通知的依据

# 08 配置与多环境管理

> 覆盖环境分层、四面隔离、环境标识传播、配置载体分层、热更新与生效可见性、默认值与兼容、配置灰度与回滚、密钥与凭据。
> **本维度定义「四面隔离」「配置载体分层」「生效可见性」三个概念，其余维度引用不重述。**

## 概念定义

| 概念 | 定义 |
|---|---|
| **四面隔离** | 环境隔离必须同时覆盖流量、数据、配置、凭据四个面。任一面未隔离即视为未隔离 |
| **配置载体分层** | 按「变更频率」与「生效方式」把配置项分派到不同载体：不变量、环境量、业务量三层，每项归属唯一一层 |
| **生效可见性** | 配置当前实际生效值可被外部确认。**「已下发」不等于「已生效」**，无法确认生效值即视为不可见 |

---

## 一、环境分层与标识

### 必须

- **`必须[H]`** 环境分层与命名必须全局统一，全部服务、配置、制品使用同一套环境标识。**违反的表现**：同一环境在不同系统中有不同名称，配置与制品错配
- **`必须[H]`** 运行实例必须能自证所处环境，环境标识可从运行时获取。**违反的表现**：无法确认实例属于哪个环境，故障时误操作
- **`必须[H]`** 环境标识必须随链路上下文传播，跨服务调用可识别来源环境。链路上下文定义见 `07-observability`。**违反的表现**：跨环境调用发生时无从发现
- **`必须[H]`** 环境标识不得由代码常量或构建期固定值决定，必须由运行时注入。**违反的表现**：同一制品无法在多环境复用，或部署到错误环境而不自知

### 推荐

- 环境标识作为日志与指标的基线维度
- 非生产环境在对外可见处有显著标识，避免误认为生产

## 二、四面隔离

### 必须

- **`必须[H]`** 非生产环境的配置不得指向生产资源。**违反的表现**：非生产的测试与压测直接作用于生产数据
- **`必须[H]`** 环境隔离必须同时覆盖流量、数据、配置、凭据四面，任一面未隔离即判定为未隔离。**违反的表现**：流量已隔离但共用同一数据存储，非生产操作污染生产数据
- **`必须[H]`** 服务发现与寻址必须受环境约束，非生产实例不得解析到生产实例。寻址要求见 `05-discovery-routing`。**违反的表现**：非生产压测流量打到生产
- **`必须[H]`** 凭据必须按环境独立签发，不得跨环境复用同一份凭据。**违反的表现**：非生产环境凭据泄露导致生产失守
- **`必须[H]`** 非生产环境不得持有可写生产数据的权限。**违反的表现**：非生产误操作直接损坏生产数据

### 推荐

- 隔离在基础设施层实施，不依赖应用层自觉判断
- 跨环境访问需求显式登记并单向受控，默认全部拒绝
- 非生产环境使用脱敏数据，不直接复制生产数据

## 三、配置载体分层

### 必须

- **`必须[H]`** 每个配置项必须按载体分层规则归属唯一一层，不得在多处重复定义。**违反的表现**：同一配置项存在多个副本，改一处不生效
- **`必须[H]`** 载体选择必须遵循：真正不变的量入代码；随环境变化、变更需重启的量入环境配置；运行期需调整、变更不重启的量入配置中心。**违反的表现**：需要热调整的开关写死在代码中，故障时无法快速处置
- **`必须[H]`** 每个配置项必须有明确的责任人与用途说明。**违反的表现**：无人敢改也无人敢删的遗留配置持续累积
- **`必须[H]`** 配置项的真实生效来源必须唯一且可查明。**违反的表现**：多个载体同时提供同名配置，实际生效值取决于加载顺序

### 推荐

- 配置项清单集中维护，随代码变更同步
- 载体层级在配置项命名或分组上可直接区分

### 参考

- 三层载体划分示例与配置项登记模板 → `examples/`

## 四、配置完备性与默认值

### 必须

- **`必须[H]`** 环境矩阵的必填项必须逐环境齐全，新增环境或新增配置项时同步补齐。**违反的表现**：某个环境缺项，该环境启动失败或以意外默认值运行
- **`必须[H]`** 交付物中不得残留未渲染的占位符。**违反的表现**：占位符被当作字面值使用，指向不存在的资源
- **`必须[H]`** 新增配置项必须有安全默认值，旧配置在新代码下必须可正常运行。兼容性总则见 `03-change-compatibility`。**违反的表现**：新代码读不到新配置项直接启动失败
- **`必须[H]`** 配置缺失或非法时行为必须可预期：要么使用默认值并告警，要么拒绝启动并给出明确原因，不得以零值或空值静默继续。**违反的表现**：超时配置缺失退化为零值，调用立即失败或永不超时
- **`必须[H]`** 配置加载失败必须显式暴露，不得吞掉异常继续运行。**违反的表现**：配置整段未加载，服务以全部默认值运行且无任何提示
- **`必须[H]`** 配置项的取值约束（类型、值域、枚举、必填性）必须显式声明并在加载时校验。**违反的表现**：非法值进入运行期，在业务处理中才引发异常

### 推荐

- 新增配置项的默认值按「保持变更前行为」选取
- 配置结构定义与代码同源，避免两处维护
- 启动时输出已加载配置项清单（敏感项脱敏）

### 参考

- 配置结构定义与环境矩阵模板 → `examples/`

## 五、热更新与生效可见性

### 必须

- **`必须[H]`** 支持热更新的配置项必须提供生效可见性：可从外部确认当前实际生效值。**违反的表现**：下发成功但服务未应用，双方均认为已生效
- **`必须[H]`** 热更新失败必须保留上次有效值并产生告警，禁止静默失败，禁止回退为空值。告警要求见 `07-observability`。**违反的表现**：更新失败后服务以空配置运行，行为异常且无信号
- **`必须[H]`** 配置变更必须产生可观测事件，记录变更项、变更时间与新值摘要。**违反的表现**：服务行为突变但无法与配置变更关联
- **`必须[H]`** 热更新必须保证一致性：一组关联配置项要么整体生效要么整体不生效。**违反的表现**：部分生效导致配置组合非法
- **`必须[H]`** 热更新不得中断在途请求，不得导致连接或缓存全量重建引发抖动。**违反的表现**：一次配置推送引发瞬时故障

### 推荐

- 提供只读的配置回读入口，用于确认生效值
- 热更新前做校验，校验不通过则不应用
- 变更前后的差异在事件中体现，便于回溯

### 参考

- 生效可见性实现方式与配置变更事件格式 → `examples/`

## 六、配置变更、灰度与回滚

### 必须

- **`必须[H]`** 生产配置变更必须经审批并可灰度，禁止一次性全量下发。发布策略要求见 `13-delivery-release`。**违反的表现**：一次错误配置瞬间影响全部实例
- **`必须[H]`** 配置必须可回滚到指定历史版本，回滚路径在变更前即确认可用。**违反的表现**：出问题后只能手工回忆原值
- **`必须[H]`** 配置版本必须与制品版本可关联，能回答「某次变更时生效的是哪份配置」。可追溯要求见 `13-delivery-release`。**违反的表现**：故障复盘无法还原当时配置
- **`必须[H]`** 配置向前兼容是可回滚的前提：新增项不得改变既有项语义，使旧制品能在新配置下运行。**违反的表现**：回滚代码后配置不兼容，被迫同时回滚两者
- **`必须[H]`** 配置变更必须留下操作记录，含变更人、变更时间、变更内容。**违反的表现**：配置被改但无人知晓来源

### 推荐

- 配置变更与制品发布使用同一套变更流程与记录
- 灰度期间观测关键指标，达标后再扩大范围
- 高风险配置项标注并要求额外确认

### 参考

- 配置灰度流程与回滚核对表 → `examples/`

## 七、密钥与凭据

### 必须

- **`必须[H]`** 凭据仅从运行时环境注入，不得写入代码、配置文件、构建产物、日志与错误信息。安全总则见 `14-security-baseline`。**违反的表现**：凭据随代码分发，泄露面覆盖全部有仓库权限者
- **`必须[H]`** 凭据必须可轮转，轮转过程不得要求停服。**违反的表现**：凭据泄露后因无法平滑更换而长期不换
- **`必须[H]`** 凭据必须遵循最小权限，按用途与环境分别签发。**违反的表现**：一份高权限凭据被所有场景共用
- **`必须[H]`** 示例、文档与模板中一律使用占位符，不得出现任何真实凭据。**违反的表现**：文档中的真实凭据被复制到多处

### 推荐

- 凭据设有效期并定期轮转
- 凭据获取与使用产生审计记录
- 本地开发使用独立的低权限凭据

### 参考

- 凭据注入方式与轮转流程 → `examples/`

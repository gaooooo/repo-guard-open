# 01 编码基线

> 覆盖命名与可读性、模块与分层、函数规模与复杂度、注释与文档、格式化、禁用构造。
> **本维度定义「一致性优先」「禁用构造」两个概念，其余维度引用不重述。**

## 概念定义

| 概念 | 定义 |
|---|---|
| **一致性优先** | 当个人偏好与项目既有模式冲突时，**以项目既有模式为准**。新代码的正确性标准之一是「看起来像是同一个人写的」 |
| **禁用构造** | 在本项目中一律不允许出现的写法。判据是「几乎不存在正当用途，且误用代价高」，而非「不够优雅」 |

---

## 一、命名与可读性

### 必须

- **`必须[H]`** 命名必须表达意图，能回答「这是什么」或「这做什么」。**违反的表现**：需要读实现才能知道一个标识符代表什么
- **`必须[H]`** 同一概念在整个项目中使用同一名称，不得混用近义词。**违反的表现**：同一事物有多个名字，检索时遗漏
- **`必须[H]`** 不得使用无约定的缩写与单字母命名（循环下标等公认惯例除外）。**违反的表现**：新人需要逐个猜测标识符含义
- **`必须[H]`** 命名不得与实际行为不符。行为变更后必须同步更新命名。**违反的表现**：名为查询的函数实际执行了写入
- **`必须[H]`** 布尔量命名必须表达肯定语义，避免双重否定。**违反的表现**：判断条件需要在头脑中做二次取反，易错
- **`必须[H]`** 魔法值必须具名，不得在逻辑中直接出现无解释的字面量。**违反的表现**：无人知道某个字面量的来历，不敢修改

### 推荐

- 命名长度与作用域范围匹配：作用域越大，名称越完整
- 集合类命名体现其元素含义与复数性
- 术语表集中维护，业务概念的译名统一

## 二、模块与分层

### 必须

- **`必须[H]`** 模块划分必须有明确的职责边界，每个模块可用一句话说明其职责。**违反的表现**：出现承载一切的通用模块，任何改动都落在其中
- **`必须[H]`** 分层依赖必须单向，禁止循环依赖。**违反的表现**：模块无法独立测试与独立演进
- **`必须[H]`** 禁止跨层直连，上层不得绕过中间层直接访问下层内部。**违反的表现**：分层形同虚设，底层变更影响面不可控
- **`必须[H]`** 模块对外暴露的接口必须最小化，内部实现不得被外部依赖。**违反的表现**：内部结构被外部引用，无法重构
- **`必须[H]`** 业务逻辑不得与外部依赖访问代码混杂，须可在不接触外部依赖的情况下被测试。可测性要求见 `11-quality-testing`。**违反的表现**：测试一段业务判断需要准备完整的外部环境
- **`必须[H]`** 新增代码必须放入职责匹配的既有模块；确需新建模块时须说明理由。**违反的表现**：模块数量随人数增长，同类逻辑分散多处

### 推荐

- 按业务能力划分模块，而非按技术角色划分
- 模块间通过明确定义的数据结构交互，不传递内部对象
- 公共模块的变更须评估全部使用方

- 分层模型与模块划分示例 → `examples/`

## 三、函数与复杂度

### 必须

- **`必须[H]`** 单个函数只做一件事，函数名能完整概括其行为而无需使用连接词。**违反的表现**：函数名出现多个动词，调用方无法预期其全部行为
- **`必须[H]`** 嵌套层次必须受控，深层嵌套须通过提前返回或提取函数消除。**违反的表现**：核心逻辑埋在多层缩进中，边界条件难以核对
- **`必须[H]`** 函数不得有未在签名或文档中体现的隐式行为（修改全局状态、依赖调用顺序）。**违反的表现**：调整调用顺序导致行为变化，原因难以定位
- **`必须[H]`** 参数个数超限时必须聚合为结构化参数，不得继续追加。**违反的表现**：调用处参数含义靠位置记忆，传错不报错
- **`必须[H]`** 禁止使用布尔参数切换函数的核心行为。**违反的表现**：调用处只见一个布尔字面量，读代码无法判断其含义

### 推荐

- 提取函数优先于添加注释来解释复杂逻辑
- 纯计算逻辑与副作用操作分离在不同函数中
- 复杂条件判断提取为具名判定函数

## 四、注释与文档

### 必须

- **`必须[H]`** 对外暴露的接口、函数、类型必须有文档注释，说明用途、参数含义、返回值、错误情形与副作用。**违反的表现**：使用方只能读实现，且会依赖实现细节
- **`必须[H]`** 注释必须解释「为什么」，不得复述代码已表达的「做了什么」。**违反的表现**：注释与代码重复，代码改动后注释成为错误信息
- **`必须[H]`** 非显而易见的决策（绕过已知问题、特殊取值、性能取舍）必须有注释说明依据。**违反的表现**：后人视其为无用代码而删除，问题重现
- **`必须[H]`** 注释必须与代码同步更新，禁止保留与实现不符的注释。**违反的表现**：错误注释比无注释危害更大
- **`必须[H]`** 禁止提交被注释掉的代码块。历史版本由版本控制承担。**违反的表现**：无人敢删，长期堆积且干扰检索
- **`必须[H]`** 遗留待办标记必须关联到具体的跟踪条目，不得只写一句待办。**违反的表现**：待办永久滞留，无人知晓其上下文与责任人

### 推荐

- 复杂算法在实现处附简要说明或引用来源
- 文档注释包含典型用法示例
- 模块入口处有一段说明其职责与边界的概述

### 参考

- 文档注释模板与注释反例 → `examples/`

## 五、格式化与风格一致性

### 必须

- **`必须[H]`** 动手前必须先阅读所在模块的既有实现，新代码风格与之一致。**违反的表现**：同一文件内存在多种风格，阅读成本上升
- **`必须[H]`** 不得在功能变更中夹带格式调整。格式统一须作为独立变更提交。变更纪律见 `03-change-compatibility`。**违反的表现**：真实改动淹没在格式差异中
- **`必须[H]`** 静态检查告警必须修复；确需抑制时须就地注明理由并限定最小范围。**违反的表现**：全局关闭规则，该规则从此永久失效
- **`必须[H]`** 重复代码达到阈值时必须提取复用；但仅出现两处且语义不同的代码不得强行合并。**违反的表现**：错误抽象产生的耦合比重复更难拆解

### 推荐

- 格式化在提交前自动执行，不依赖人工记忆
- 静态检查规则集全项目统一，不按目录例外
- 新增规则时一次性修复存量问题，避免长期混杂

- 风格一致性核对方法 → `examples/`

## 六、禁用构造

### 必须

- **`必须[H]`** 禁止忽略错误返回值。确需忽略时必须显式表达并注明理由。**违反的表现**：失败被静默吞掉，问题在远离故障点处暴露
- **`必须[H]`** 禁止捕获异常后不做任何处理。捕获必须伴随处理、转换或上报之一。错误处理要求见 `02-error-handling`。**违反的表现**：异常消失，行为异常但日志干净
- **`必须[H]`** 禁止在库代码与业务逻辑中直接终止进程。终止决策只能由程序入口层做出。**违反的表现**：深层逻辑的一个分支导致整个服务退出
- **`必须[H]`** 禁止使用可变全局状态承载业务数据。**违反的表现**：并发访问产生难以复现的数据错乱
- **`必须[H]`** 禁止依赖未定义行为与实现细节（迭代顺序、默认精度、平台相关默认值）。**违反的表现**：换环境或换版本后行为变化
- **`必须[H]`** 禁止以固定等待代替状态确认。**违反的表现**：等待时间在不同负载下或过短或过长，偶发失败
- **`必须[H]`** 禁止提交调试残留（临时输出、临时开关、指向个人环境的地址）。**违反的表现**：调试输出进入生产日志，或临时开关意外生效

### 推荐

- 禁用构造清单随踩坑经验持续补充，每项注明来由
- 新增禁用项时同步提供替代写法
- 对既有违例做一次性清理，不允许新增

### 参考

- 禁用构造清单与替代写法 → `examples/`

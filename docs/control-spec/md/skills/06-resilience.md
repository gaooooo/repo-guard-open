# 06 韧性治理

> 覆盖超时、重试、熔断、限流、降级与隔离、背压、故障演练。
> **本维度定义「超时预算」「强依赖 / 弱依赖」「降级预案」三个概念，其余维度引用不重述。**

## 概念定义

| 概念 | 定义 |
|---|---|
| **超时预算** | 一个入口请求允许消耗的总时长上限。自入口向下逐层分配，每层的下游超时之和加处理余量不得超过本层预算 |
| **强依赖** | 不可用则本服务对应功能不可用的依赖 |
| **弱依赖** | 不可用时本服务可降级继续提供服务的依赖 |
| **降级预案** | 三元组：触发条件、降级后行为、恢复条件。三者缺一即不成立 |

## 一、超时

### 必须

- **`必须[H]`** 所有跨进程调用必须带显式超时，不得使用无超时调用或依赖底层默认值。**违反的表现**：单个慢依赖拖垮整条链路，资源无法释放
- **`必须[H]`** 超时不得倒挂：上游超时须不小于下游串行之和加余量。**违反的表现**：上游已超时放弃，下游仍在处理无人接收的请求
- **`必须[H]`** 每个对外入口必须声明超时预算，并在设计文档或配置中可查。**违反的表现**：入口无预算声明，下游超时由各调用点各自拍定
- **`必须[H]`** 超时预算自入口向下逐层递减分配，下游层不得使用等于或大于上游层的超时。**违反的表现**：上游超时耗尽时下游仍在等待，产生无人接收的在途请求
- **`必须[H]`** 超时时长必须按依赖的实际响应分布设定，并记录设定依据。**违反的表现**：全局套用同一个默认值，与依赖实际表现无关
- **`必须[H]`** 超时必须覆盖调用全过程（含连接建立、请求发送、响应接收），不得只设其中一段。**违反的表现**：只设读超时，连接阶段可无限等待
- **`必须[H]`** 超时触发后必须释放其占用的资源（连接、缓冲、协程或线程），不得仅放弃等待。**违反的表现**：超时返回但底层调用继续运行，压力持续累积

### 推荐

- 超时预算在链路上预留处理余量，不将预算全额分配给下游
- 批量与流式接口按单位规模声明超时，不使用固定总时长
- 超时时长作为配置项而非代码常量，便于按环境调整

## 二、重试

### 必须

- **`必须[H]`** 重试必须带退避与次数上限，并在实现处标注其幂等依据。**违反的表现**：无上限重试在依赖故障时形成雪崩
- **`必须[H]`** 重试仅用于幂等操作；非幂等操作重试必须由幂等键保护。幂等语义定义见 `04-api-contract`。**违反的表现**：写操作直接重试，产生重复数据
- **`必须[H]`** 仅对可重试错误重试。参数非法、权限不足、业务规则拒绝等确定性失败不得重试。**违反的表现**：对必然再次失败的请求反复重试，放大下游压力
- **`必须[H]`** 重试必须继承剩余超时预算，不得为重试额外延长总耗时。**违反的表现**：重试次数乘以单次超时超出入口预算，上游早已超时
- **`必须[H]`** 重试必须带退避，禁止在循环中无间隔连续重试。**违反的表现**：依赖抖动时重试洪峰将其彻底压垮
- **`必须[H]`** 多层链路中重试不得逐层叠加。重试层级必须显式约定并记录。**违反的表现**：三层各重试三次，底层实际承受数十倍请求

### 推荐

- 设置全局重试预算，限制重试请求占总请求的比例上限
- 退避加入随机抖动，避免多实例重试时刻对齐
- 重试次数与退避参数作为配置项，可在故障期间临时收紧

### 参考

- 可重试错误与不可重试错误的分类方法 → `examples/`

## 三、熔断

### 必须

- **`必须[H]`** 每个强依赖必须配置熔断。**违反的表现**：依赖持续超时，调用方资源被长期占用直至耗尽
- **`必须[H]`** 必须显式区分强依赖与弱依赖，并在设计文档中列明。**违反的表现**：依赖分级缺失，无法判断哪些故障应降级、哪些应失败
- **`必须[H]`** 熔断必须定义打开条件、半开探测方式、恢复条件三项。**违反的表现**：只配打开阈值，熔断后无法自动恢复
- **`必须[H]`** 熔断打开期间必须走降级路径，不得直接抛出原始错误给调用方。**违反的表现**：熔断只是把慢失败变成快失败，对调用方无改善
- **`必须[H]`** 熔断状态变化必须产生可观测信号。上报要求见 `07-observability`。**违反的表现**：熔断已打开但无人知晓，故障定位从零开始

### 推荐

- 熔断粒度细化到依赖的单个接口或单个实例，而非整个依赖
- 半开探测使用少量流量而非全量放行
- 熔断参数支持运行时调整，无需重新发布

### 参考

- 熔断状态机与参数选取方法 → `examples/`

## 四、限流

### 必须

- **`必须[H]`** 每个对外入口必须配置限流。**违反的表现**：流量突增直接压垮服务，无自保能力
- **`必须[H]`** 限流必须声明保护对象（自身容量或下游容量）与配额口径（按调用方、按接口、按资源维度）。**违反的表现**：只有一个全局阈值，单一调用方可耗尽全部配额
- **`必须[H]`** 被限流的请求必须返回可识别的、区别于系统故障的响应，并告知调用方可否重试。错误码要求见 `04-api-contract`。**违反的表现**：限流与故障返回相同错误，调用方持续重试加剧过载
- **`必须[H]`** 出流量必须受控：对下游的并发与速率有上限，不得无限放大。**违反的表现**：自身流量激增时将下游打垮
- **`必须[H]`** 限流触发必须产生可观测信号。**违反的表现**：请求被静默丢弃，调用方只见超时

### 推荐

- 按调用方分配配额，重要调用方与非重要调用方隔离
- 优先使用基于实际负载的自适应限流，静态阈值作为兜底
- 限流阈值支持运行时调整

### 参考

- 限流算法对照与配额划分方法 → `examples/`

## 五、降级与隔离

### 必须

- **`必须[H]`** 每个强依赖必须有降级预案，完整给出触发条件、降级后行为、恢复条件三项。**违反的表现**：只写「失败时降级」，不说明降级成什么
- **`必须[H]`** 降级后行为必须明确对业务语义的影响（返回缺省值、返回部分结果、拒绝服务），并确认业务可接受。**违反的表现**：降级返回空值被下游当作正常结果，产生错误业务判断
- **`必须[H]`** 降级必须可人工强制开启与关闭，不得只能由自动条件触发。**违反的表现**：已知依赖故障但无法提前降级，只能等自动条件触发
- **`必须[H]`** 弱依赖故障不得导致主流程失败。**违反的表现**：非关键功能异常导致整个请求失败
- **`必须[H]`** 关键路径与非关键路径必须做资源隔离，不共享同一组会被耗尽的资源。**违反的表现**：非关键功能占满连接池，关键功能无资源可用
- **`必须[H]`** 降级状态必须可观测，且降级期间不得停止上报原始故障信息。**违反的表现**：降级掩盖故障，问题长期不被发现

### 推荐

- 降级预案随依赖变更同步更新，作为依赖引入的前置条件
- 按依赖或按业务分组划分资源池，单组耗尽不影响其余组
- 降级开关默认关闭，开启与关闭均产生变更记录

### 参考

- 降级预案模板与资源隔离划分方法 → `examples/`

## 六、背压与资源上限

### 必须

- **`必须[H]`** 所有队列、缓冲、并发单元、连接池必须设容量上限。**违反的表现**：请求堆积直至资源耗尽
- **`必须[H]`** 容量达到上限时必须有明确的处置策略（拒绝、阻塞、丢弃最旧），不得无声堆积。**违反的表现**：堆积在内存中不可见，直到进程异常终止
- **`必须[H]`** 排队等待必须设等待上限，超出即放弃。**违反的表现**：请求在队列中等待超过调用方超时，处理完已无人接收
- **`必须[H]`** 消费能力不足时必须向上游传导压力，不得只在本层堆积。**违反的表现**：上游持续投递，本层积压不断增长

### 推荐

- 队列长度、等待时长、拒绝量作为常态监控指标
- 容量上限按实际资源核算设定，并记录核算依据
- 长耗时操作改为异步处理，避免占用同步链路资源

### 参考

- 背压传导方式与容量核算方法 → `examples/`

## 七、故障演练

### 必须

- **`必须[H]`** 每个降级预案必须至少验证一次有效性，并留下验证记录。**违反的表现**：预案只存在于文档，真实故障时不生效
- **`必须[H]`** 验证记录必须写明验证方式与结论；未实际验证的不得表述为已验证。诚实标注要求见 `15-ai-execution-discipline`。**违反的表现**：以「逻辑上应当可行」代替实际验证

### 推荐

- 强依赖故障、依赖超时、依赖返回异常数据三类场景纳入常态演练
- 演练在与生产同构的环境进行，覆盖真实配置
- 依赖清单或降级预案变更时重新验证

### 参考

- 演练场景清单与验证记录模板 → `examples/`

# 10 工程文档

> 覆盖文档体系与职责边界、同步义务、设计文档、变更记录、使用与运行文档、文档质量、组织与演进。
> **本维度定义「文档分层」「同步义务」「文档腐化」三个概念，其余维度引用不重述。**
>
> 分工：本维度管**工程文档的产出与维护**；代码注释归 `01-coding-baseline`；
> 接口契约文档归 `04-api-contract`；文档的自审归 `12-self-review`；变更说明与提交信息归 `13-delivery-release`。

## 概念定义

| 概念 | 定义 |
|---|---|
| **文档分层** | 按受众与问题分四层：**入口文档**（这是什么、怎么开始）、**设计文档**（为什么这样做、怎么组织的）、**变更记录**（发生过什么、为什么改）、**使用与运行文档**（怎么用、出问题怎么办）。每层受众不同，不得混写 |
| **同步义务** | 文档与实现的一致性由**变更方在同一次变更中**保证。文档更新不是后续任务，而是变更的组成部分 |
| **文档腐化** | 文档与实现不一致。⚠️ **错误文档比无文档危害更大**——无文档时人会去读实现，错误文档让人不读实现就下结论 |

## 一、文档体系与职责边界

### 必须

- **`必须[H]`** 项目必须有入口文档，回答「这是什么、解决什么问题、怎么开始」，并指向其余文档。**违反的表现**：新人无从下手，只能逐个问人
- **`必须[H]`** 每层文档的职责边界必须明确，同一内容只在一处维护。**违反的表现**：同一说明存在多份副本，改一处其余成为错误信息
- **`必须[H]`** 入口文档不得承载详细内容，只做导航。**违反的表现**：入口文档膨胀为万能文档，读者找不到重点且维护成本极高
- **`必须[H]`** 文档必须声明其受众。面向使用方与面向维护方的内容不得混写。**违反的表现**：使用方被内部实现细节淹没，维护方找不到设计依据
- **`必须[H]`** 文档存放位置必须统一且可预期，不得散落在各处。**违反的表现**：同类文档分散在多个位置，检索靠记忆
- **`必须[H]`** 文档必须纳入与代码同一套版本控制，不得只存在于外部系统。**违反的表现**：无法回溯某个版本当时的文档状态，评审也看不到文档改动

### 推荐

- 文档层级与目录结构固定，新增文档有明确归属位置
- 外部协作文档与工程文档建立单向引用，避免双向同步
- 文档入口处标注适用范围与最后核对时间

## 二、同步义务

### 必须

- **`必须[H]`** 文档更新必须与对应变更在同一次提交中完成，不得延后为后续任务。**违反的表现**：文档欠账持续累积，最终无人愿意补
- **`必须[H]`** 必须显式定义「何种变更须更新何种文档」的对应关系，并在变更时逐条对照。**违反的表现**：是否需要更新文档全凭个人判断，同类变更处置不一
- **`必须[H]`** 以下变更必须同步更新设计文档：新增或调整模块、变更模块职责与依赖关系、修改核心流程与数据流、变更技术选型、修改数据模型、调整部署与环境要求。**违反的表现**：设计文档停留在初版，与实际系统渐行渐远
- **`必须[H]`** 以下变更必须留下变更记录：新增功能、修复重要缺陷、重构核心逻辑、变更依赖与配置、重要技术决策。**违反的表现**：无法回答「这个设计为什么是现在这样」
- **`必须[H]`** 对外行为、接口、配置项、运行方式发生变化时，必须同步更新使用与运行文档。**违反的表现**：使用方按旧文档操作失败
- **`必须[H]`** 文档更新范围必须与本次改动范围一致，不得只更新主要部分。改动范围要求见 `15-ai-execution-discipline`。**违反的表现**：主流程文档已更新而边角说明仍是旧的
- **`必须[H]`** 变更未触发文档更新时，须能说明为何不需要，不得默认跳过。**违反的表现**：应更新而未更新与确实无需更新无法区分

### 推荐

- 文档更新与代码改动在同一次评审中一并审查
- 变更类型与文档更新的对应关系形成清单，作为自审检查项
- 文档改动在变更说明中单列，便于评审者定位

### 参考

- 变更与文档更新对应表 → `examples/`

## 三、设计文档

### 必须

- **`必须[H]`** 设计文档必须覆盖：整体结构与模块划分、各模块职责与依赖关系、核心流程与数据流、关键技术选型、数据模型、部署与环境要求。**违反的表现**：只有零散的局部说明，无人掌握全貌
- **`必须[H]`** 关键决策必须记录理由与当时的约束条件，不得只写结论。**违反的表现**：后人不知能否调整，设计变成不敢碰的黑盒
- **`必须[H]`** 已评估但未采纳的方案必须记录及其否决理由。**违反的表现**：后人重复评估已被否决的方案，或误以为从未考虑过
- **`必须[H]`** 设计文档必须描述当前实际状态，不得保留已废弃的设计描述。**违反的表现**：读者按废弃设计理解系统，得出错误结论
- **`必须[H]`** 已知缺陷、未完成部分与技术债必须显式登记，不得只写理想状态。**违反的表现**：读者以为系统已完备，在缺口处踩坑
- **`必须[H]`** 模块的对外契约与内部实现在文档中必须分离描述。**违反的表现**：使用方依赖内部实现细节，重构即破坏使用方
- **`必须[H]`** 图示必须与正文同步更新，不得保留过期图示。**违反的表现**：图与文字互相矛盾，读者无从判断哪个为准

### 推荐

- 设计文档先给结论与整体图景，再给论证过程
- 重大决策独立成篇记录，含背景、备选、选择、影响
- 跨模块的约定集中描述，不在各模块中分别重复

### 参考

- 设计文档结构模板与决策记录格式 → `examples/`

## 四、变更记录

### 必须

- **`必须[H]`** 变更记录必须按时间顺序组织，可定位到任一时点的变更情况。**违反的表现**：无法回溯问题引入的时间与背景
- **`必须[H]`** 每条记录必须包含：变更内容、变更原因、影响范围。**违反的表现**：只记录改了什么，无法判断为何改、影响谁
- **`必须[H]`** 破坏性变更、迁移要求、技术决策必须在记录中显式标注。**违反的表现**：使用方在升级后才发现不兼容
- **`必须[H]`** 变更记录必须可关联到具体的需求条目与代码变更。可追溯要求见 `03-change-compatibility`。**违反的表现**：记录与实际改动对不上，无法互相印证
- **`必须[H]`** 记录必须陈述事实，不得夸大或省略失败与回退。**违反的表现**：只记成功不记反复，后人重蹈覆辙
- **`必须[H]`** 已记录的历史条目不得事后修改或删除；认知变化以新增记录的方式修正。**违反的表现**：历史被改写，无法还原当时的判断依据

### 推荐

- 记录格式统一，便于检索与自动提取
- 一次变更一条记录，不把多次变更合并为一条
- 影响范围写明具体模块、接口与配置项，而非笼统描述

### 参考

- 变更记录格式与撰写示例 → `examples/`

## 五、使用与运行文档

### 必须

- **`必须[H]`** 对外提供的能力必须有使用文档，覆盖用途、前置条件、调用方式、典型场景、错误情形。**违反的表现**：使用方只能靠读实现或反复试错
- **`必须[H]`** 使用文档中的示例必须可直接执行且经过验证，不得给出未经验证的片段。验证要求见 `11-quality-testing`。**违反的表现**：照抄示例即报错，文档失去信任
- **`必须[H]`** 必须有从零开始的上手说明，覆盖环境准备、依赖安装、本地运行、验证方式。**违反的表现**：每个新人重复消耗数天摸索环境
- **`必须[H]`** 必须有运行文档，覆盖部署方式、配置项说明、健康检查方式、常见故障与处置。**违反的表现**：出问题时只能找原作者
- **`必须[H]`** 配置项必须有文档说明其用途、取值范围、默认值与变更影响。配置要求见 `08-config-environment`。**违反的表现**：无人敢改也无人敢删的遗留配置持续累积
- **`必须[H]`** 文档中不得出现凭据、内部敏感地址与未脱敏数据，一律使用占位符。安全要求见 `14-security-baseline`。**违反的表现**：敏感信息随文档扩散至不受控范围
- **`必须[H]`** 已下线或废弃的能力必须在文档中标注，不得直接删除说明。废弃流程见 `03-change-compatibility`。**违反的表现**：使用方找不到说明，也不知道该迁移到哪里

### 推荐

- 上手说明定期实际走一遍，验证其仍然可用
- 常见问题按实际提问频率排序并持续补充
- 故障处置说明写明判断依据与预期效果，而非只列操作步骤

### 参考

- 上手说明与运行手册模板 → `examples/`

## 六、文档质量

### 必须

- **`必须[H]`** 文档中的事实性陈述必须有据可查；推断与假设必须显式标注。假设显式化见 `15-ai-execution-discipline`。**违反的表现**：推断被当作事实传递，下游据此决策
- **`必须[H]`** 文档必须能被不具备背景知识的目标读者理解，不得依赖只有作者知道的隐含前提。**违反的表现**：只有作者看得懂，交接后无人能用
- **`必须[H]`** 术语必须全局统一，与既有术语表一致；首次出现的专有概念须给出定义。**违反的表现**：同一事物多个称呼，读者以为是不同东西
- **`必须[H]`** 文档内与文档间的引用必须有效，不得指向不存在的位置。**违反的表现**：引用链断裂，读者无法继续深入
- **`必须[H]`** 文档之间不得自相矛盾；发现矛盾必须确认哪一处正确并同步修正。**违反的表现**：两处描述冲突，读者随机采信其一
- **`必须[H]`** 不得生成无信息量的文档内容——复述标题、堆砌套话、罗列显而易见的事实。**违反的表现**：篇幅可观但阅读价值为零，且掩盖真正重要的内容
- **`必须[H]`** 文档篇幅必须与内容价值相称，冗余部分予以删减。**违反的表现**：读者放弃阅读，文档等同不存在

### 推荐

- 结论先行，先给要点再给论证
- 能用表格表达的不用段落，能用一行说清的不写三行
- 面向读者会提的问题组织内容，而非按作者的思考顺序

- 文档写作检查清单与常见冗余模式 → `examples/`

## 七、组织与演进

### 必须

- **`必须[H]`** 必须显式定义文档拆分的触发条件，达到条件即拆分为独立文档。**违反的表现**：单份文档无限膨胀，检索与维护成本失控
- **`必须[H]`** 拆分时原文档必须保留简介与跳转，详细内容迁移且不重复。**违反的表现**：拆分后两处各留一份，很快产生分歧
- **`必须[H]`** 拆分与合并本身属于结构变更，必须记入变更记录。**违反的表现**：文档结构变动无人知晓，旧引用失效
- **`必须[H]`** 不满足拆分条件的内容不得为拆而拆。**违反的表现**：文档碎片化，读者需跳转多次才能拼出完整图景
- **`必须[H]`** 长期内容稀少且无新增迹象的独立文档必须合并回上级文档。**违反的表现**：大量空壳文档占据目录，掩盖真正有内容的部分
- **`必须[H]`** 文档更新必须为增量式，不得无必要地大规模重写既有内容。最小改动要求见 `03-change-compatibility`。**违反的表现**：改动比对全是重排，评审者无法识别真实变化
- **`必须[H]`** 文档结构调整不得丢失既有内容；确需删除的须说明理由。**违反的表现**：重构文档时静默丢失关键说明

### 推荐

- 拆分条件量化表达（篇幅、小节数、对外暴露项数、是否有独立流程或运行方式）
- 文档目录结构与代码模块结构保持对应，便于定位
- 定期检查文档有效性，清理已无对应实现的内容

### 参考

- 拆分与合并阈值示例、文档结构演进记录 → `examples/`

# 02 错误处理

> 覆盖错误分类与建模、产生与包装、传播与转换、处理与恢复、资源清理、部分失败、并发与异步中的错误。
> **本维度定义「错误分层」「错误上下文」「处理点」三个概念，其余维度引用不重述。**
>
> 分工：本维度管**进程内错误如何产生、传播、被处理**；对外错误码契约归 `04-api-contract`；
> 依赖故障的应对策略（超时、重试、熔断、降级）归 `06-resilience`；错误的记录与告警归 `07-observability`。

## 概念定义

| 概念 | 定义 |
|---|---|
| **错误分层** | 错误按来源分三层：**输入错误**（调用方给的数据或参数不合法）、**依赖错误**（下游、存储、外部系统失败）、**自身错误**（本服务的逻辑缺陷或状态异常）。三层的处理策略、可重试性、告警级别完全不同 |
| **错误上下文** | 错误在传播过程中累积的定位信息：发生位置、操作对象、关键入参、失败原因、原始错误。**丢失上下文的错误等于只知道「出错了」** |
| **处理点** | 对错误做出最终决策（重试、降级、返回、终止）的位置。**一个错误只应有一个处理点**，其余位置只做传递与补充上下文 |

## 一、错误分类与建模

### 必须

- **`必须[H]`** 每个错误必须可判定属于输入错误、依赖错误、自身错误中的哪一层。**违反的表现**：无法决定该重试、该降级还是该告警，处理策略只能靠猜
- **`必须[H]`** 错误必须携带可编程判别的类型标识，不得要求调用方靠匹配错误描述文本来判断类型。**违反的表现**：错误描述措辞一改，上游的判断分支全部失效
- **`必须[H]`** 「无结果」与「失败」必须用不同方式表达，不得以空值同时表示二者。**违反的表现**：故障被当作数据不存在，触发错误的业务分支
- **`必须[H]`** 预期内的业务分支不得用错误机制表达。**违反的表现**：正常业务流程持续产生错误信号，真实错误被淹没
- **`必须[H]`** 错误类型的定义必须与其处理方式匹配：不同处理方式的错误须可区分，处理方式相同的错误不必细分。**违反的表现**：定义了几十种错误类型但处理代码只有一个分支，分类无意义
- **`必须[H]`** 不得用通用错误类型承载全部错误。**违反的表现**：调用方无法区分参数错误与系统故障，只能一律重试或一律放弃

### 推荐

- 错误类型集中定义，避免同一语义的错误在各处各自定义
- 错误层次与对外错误码的映射关系显式维护，见 `04-api-contract`
- 可重试性作为错误类型的显式属性，而非由调用方推断

### 参考

- 错误分层模型与类型设计示例 → `examples/`

## 二、错误的产生与上下文

### 必须

- **`必须[H]`** 错误产生时必须携带定位所需的上下文：操作对象标识、关键入参、失败原因。**违反的表现**：错误信息只有一句「操作失败」，排查需从零复现
- **`必须[H]`** 错误上下文不得包含敏感数据。需要标识时使用不可逆处理后的标识。数据分级见 `14-security-baseline`。**违反的表现**：错误信息随日志与响应扩散，携带凭据或个人信息
- **`必须[H]`** 向上传递错误时必须补充本层的上下文，不得原样抛出后丢失调用路径。**违反的表现**：只知道底层报错，不知道是哪条业务路径触发的
- **`必须[H]`** 包装错误时必须保留原始错误，使最终处理点能够判别根因。**违反的表现**：原始错误被替换为笼统描述，类型判断失效，可重试性丢失
- **`必须[H]`** 错误描述必须陈述事实而非猜测，不得写入未经确认的原因推断。**违反的表现**：错误信息指向错误方向，排查被带偏
- **`必须[H]`** 同一错误不得在多层重复包装相同信息。**违反的表现**：错误信息层层堆叠，有效信息被淹没

### 推荐

- 上下文以结构化字段附加，而非拼接进描述文本
- 错误描述面向排查者而非终端用户，用户可见文案由对外层单独转换
- 跨进程传递的错误保留可关联到原始链路的标识，见 `07-observability`

### 参考

- 错误包装与上下文累积示例 → `examples/`

## 三、传播与转换

### 必须

- **`必须[H]`** 每个错误必须有明确的处理点，其余位置只传递与补充上下文，不得多处各自处理。**违反的表现**：同一错误被重试两次又被降级一次，行为不可预测
- **`必须[H]`** 不得在中间层擅自吞掉错误后返回正常结果。**违反的表现**：上层认为操作成功，实际未执行
- **`必须[H]`** 跨越模块与层次边界时必须做错误转换，不得把内层实现细节的错误直接暴露给外层。**违反的表现**：上层被迫依赖下层实现细节，下层重构即破坏上层
- **`必须[H]`** 错误转换必须保持可重试性语义不变，不得把确定性失败转换为疑似可重试的错误。**违反的表现**：参数错误被包装成系统故障，上游反复重试必然再次失败
- **`必须[H]`** 对外暴露的错误必须经过转换，不得直接透传内部错误。对外错误要求见 `04-api-contract`。**违反的表现**：内部结构与实现细节外泄
- **`必须[H]`** 错误在传播过程中不得被降级为警告或提示而失去错误语义。**违反的表现**：真实失败以提示形式出现，无人跟进

### 推荐

- 转换发生在明确的边界层，而非散落在业务逻辑各处
- 同一边界上的转换规则集中维护，保证一致性

- 边界错误转换模式 → `examples/`

## 四、处理与恢复

### 必须

- **`必须[H]`** 捕获错误必须伴随处理、转换或上报之一，禁止捕获后不做任何动作。**违反的表现**：错误消失，行为异常但日志干净
- **`必须[H]`** 禁止忽略错误返回值。确需忽略时必须显式表达并注明理由。禁用构造见 `01-coding-baseline`。**违反的表现**：失败被静默吞掉，问题在远离故障点处暴露
- **`必须[H]`** 捕获范围必须精确到预期的错误类型，不得用最宽泛的捕获吞掉全部错误。**违反的表现**：预期外的严重错误被当作可恢复错误处理，问题被掩盖
- **`必须[H]`** 处理动作必须与错误层次匹配：输入错误拒绝并返回、依赖错误按韧性策略处置、自身错误上报并终止当前操作。韧性策略见 `06-resilience`。**违反的表现**：对自身逻辑缺陷做重试，重试必然再次失败
- **`必须[H]`** 不得通过重试掩盖自身逻辑缺陷。**违反的表现**：缺陷长期存在且被重试成本掩盖，直到重试也无法覆盖时才暴露
- **`必须[H]`** 错误处理路径必须保证状态一致：失败后不得留下部分修改的中间状态。事务要求见 `09-data-storage`。**违反的表现**：操作失败但数据已被部分修改，后续行为不可预期
- **`必须[H]`** 不可恢复的错误必须快速失败，不得继续执行后续逻辑。**违反的表现**：在已知错误状态下继续处理，产生错误结果并扩大影响
- **`必须[H]`** 终止进程的决策只能由程序入口层做出，库代码与业务逻辑不得直接终止进程。**违反的表现**：深层逻辑的一个分支导致整个服务退出
- **`必须[H]`** 错误必须被记录或上报至少一次，且不得重复记录同一错误。记录要求见 `07-observability`。**违反的表现**：错误无记录而无人知晓，或同一错误产生多条日志干扰定位

### 推荐

- 可恢复与不可恢复错误在类型上即可区分，无需靠处理代码判断
- 错误处理逻辑与正常逻辑在结构上清晰分离，避免正常路径被错误分支淹没
- 兜底处理存在但不承担常规错误处理职责

### 参考

- 错误处理决策表与恢复模式 → `examples/`

## 五、资源清理

### 必须

- **`必须[H]`** 已获取的资源必须在错误路径上同样被释放，释放动作与获取动作就近成对。**违反的表现**：正常路径无泄漏而错误路径泄漏，故障期间资源迅速耗尽
- **`必须[H]`** 资源释放必须覆盖全部退出路径，包括提前返回与异常退出。**违反的表现**：新增一个提前返回分支即引入泄漏，且测试不易发现
- **`必须[H]`** 清理动作自身失败不得掩盖原始错误。**违反的表现**：真正的失败原因被清理失败的错误替换
- **`必须[H]`** 清理逻辑必须可重入，重复执行不产生副作用。**违反的表现**：重复释放导致崩溃或状态错乱
- **`必须[H]`** 进程终止时必须释放外部可见的资源并完成必要的收尾。优雅下线见 `05-discovery-routing`。**违反的表现**：残留锁、残留临时数据、未提交的在途操作

### 推荐

- 使用语言提供的自动清理机制，而非依赖人工在每条路径上编写释放代码
- 资源获取与释放的配对关系在代码结构上可直接看出
- 长生命周期资源的所有权归属明确，避免多处各自释放

## 六、部分失败

### 必须

- **`必须[H]`** 批量操作必须明确失败语义：整体失败还是部分失败，并在接口契约中声明。契约要求见 `04-api-contract`。**违反的表现**：调用方无法判断哪些成功，重试导致部分重复
- **`必须[H]`** 部分失败必须逐项返回结果，不得只返回一个总体失败。**违反的表现**：调用方只能整批重试，已成功项被重复执行
- **`必须[H]`** 多步骤操作中途失败时，必须明确已完成步骤的处置：回滚、补偿或保留并标记。**违反的表现**：中间状态无人处理，数据长期处于不一致
- **`必须[H]`** 补偿动作必须可重入且自身失败可被发现。**违反的表现**：补偿失败后无人知晓，不一致状态永久保留
- **`必须[H]`** 不得以「大部分成功」为由将部分失败上报为成功。**违反的表现**：失败项被静默丢弃，数据缺失且无审计线索

### 推荐

- 部分失败的结果结构在全部批量接口中保持一致
- 失败项可被单独重试，无需整批重放
- 不一致状态有巡检与修复手段，不依赖人工发现

## 七、并发与异步中的错误

### 必须

- **`必须[H]`** 并发执行单元内部的错误必须被传递回发起方或被显式处理，不得在执行单元内消失。**违反的表现**：后台任务静默失败，主流程认为已完成
- **`必须[H]`** 并发执行单元必须有顶层的错误兜底，未处理的错误不得导致整个进程异常终止。**违反的表现**：一个后台任务的意外错误使整个服务退出
- **`必须[H]`** 多个并发操作中任一失败时，必须明确其余操作的处置：等待完成、取消、还是忽略。**违反的表现**：失败后其余操作仍在后台运行并产生副作用
- **`必须[H]`** 取消与超时必须能够真正中断执行，不得仅放弃等待而让操作继续运行。超时要求见 `06-resilience`。**违反的表现**：超时返回但底层继续执行，压力持续累积
- **`必须[H]`** 异步任务与消息消费的失败必须有明确处置：重试、留存、还是转入人工。不得静默丢弃。**违反的表现**：消息处理失败后数据缺失且无人知晓
- **`必须[H]`** 异步失败必须可观测，不得因无调用方等待而不上报。**违反的表现**：后台链路长期失败而监控无信号

### 推荐

- 并发错误聚合返回，而非只返回第一个遇到的错误
- 取消信号全链路透传，各层都能响应
- 异步失败的留存数据可直接用于重放，而非仅记录一条日志

### 参考

- 并发错误聚合与取消传播示例 → `examples/`

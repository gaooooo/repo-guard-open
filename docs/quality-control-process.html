repo-guard · quality control plane

质量提升 / 控制过程全景

核心判断：AI 写代码的质量问题，多数不是「模型不够聪明」，而是「它不知道这一改会波及什么」。影响面、红线意图、仓内既有写法，静态分析能算、模型算不出来。插件把这三类信息推进过程，并在关键事件上硬拦或提醒。

二、七道门怎么分，和 hook 什么关系

Hook 是 CodeBuddy 宿主提供的生命周期插槽（SessionStart、PreToolUse、Stop…）。门是插件自己的控制语义：每一道回答一个问题。映射是多对多——一道门可以挂多个 hook，一个 hook 也可以同时服务几道门。

门回答的问题主要 hook插件动作
L0 注入面开干前，模型知不知道本仓约束？SessionStart · UserPromptSubmit · PostCompactadditionalContext 推注入。不拦。
L1 准入门这次写入允不允许开始？PreToolUse（写工具 / Bash）公共层未查 impact → deny。红线/禁改/范围默认关。
L2 执行门这条命令能不能真正跑？宿主 permissions / sandbox（不是插件 hook）插件永久不做，避免两套规则打架。
L3 循环门是不是卡住空转？PostToolUse / PostToolUseFailure 计数，PreToolUse 短路重复 3 / 连败 3 可 deny。默认关，计数始终记。
L4 诚实信号这一轮实际怎么结束的？Stop · SessionEnd只观测。看不到宿主 finalReason，只能近似。
L5 交付门交付是否可接受？Stop查本会话有没有 lint/test/build 证据。默认只提醒。
L6 治理留痕这些门有没有在做有用功？所有已实现 hook 写 metrics，SessionEnd 收尾写入 HOME/metrics.ndjson，governance 出报表。

切分依据：问题，不是事件

  • L0 知道约束 → L1 这次能不能动 → L2 命令能不能跑 → L3 有没有空转 → L4 怎么收场 → L5 交得出去吗 → L6 门禁有没有用。
  • 所以是 7 道，编号 L0–L6。L0 从 0 起，因为它发生在任何工具调用之前。
  • UserPromptSubmit 属于 L0（按任务再推一截），不是单独一道门。

一个 hook 服务多道门的例子

  • PreToolUse：先走 L3 循环短路，再走 L1 红线/范围/公共层。
  • PostToolUse：L3 更新计数 + 超长提醒 + L6 埋点。
  • Stop：L5 交付提醒 + L3 迭代摘要 + L4 近似信号。
  • Hook 是管子，门是管子里流过的判定。

三、质量提升闭环：先体检，再注入，最后才硬拦

装完就开始拦人的护栏，人的第一反应是卸载。升档顺序写死在 docs/STANDARDS.md §8。

1. 体检

init / scan

技术栈、超长文件、循环依赖、推测公共层。默认一个字节不写。

2. 人确认

init --write

生成 repo-facts。公共层是推测，猜错要么漏拦要么天天误伤。

3. 意图进仓

redlines + audit

人写意图，机器验完整性：守空气 / paths 后门 / evidence 失准。

4. 只提醒

standards init

五端规范铺进项目层。maxSeverity 默认 remind，铺完不会有新拦截。

5. 看数据

governance

这些门在做有用功还是在骚扰人。没有数据不要开硬拦。

6. 逐条升档

ask → block

每开一条先看误伤。block 还要过准入三条件，否则自动降级。

两层配置，两种生效

  • 运行时合并：standards/ 全局层直接被读，项目层按 id 字段级覆盖。
  • 一次性拷贝：redlines / guard / repo-facts 靠 init 拷到项目层。
  • 升级插件不会把新红线偷偷塞进已有仓库。

四层配置面

  • 身份 团队是谁：章程、岗位 → 推
  • 能力 加一项更能干：项目知识、任务路由、图谱 → 推 / 按任务 / 拉
  • 约束 加一项更受限：禁忌、红线、禁改、范围 → 推 / 硬
  • 流程 活怎么进来怎么收：图谱强制、循环、交付、复述 → 软 / 硬

验收闸门

  • doctor：JSON、僵尸条目、注入配额、静默降级
  • verify-hooks：59 条，拦得对且不误伤
  • audit：红线腐烂检测
  • 脚本测代码，真机测宿主怎么用它。

六、L0–L6 各门控制点

每道门写清拦什么、不拦什么、默认值、以及为什么。配置骨架在 templates/guard/，除 L0 / L6 外全部默认关。

七、研发规范：强度 × 时机 × 落点

红线只有一种强度（命中就拦）。规范多一个问题：这条能不能拦。block 级编译成 PolicyRule，交给同一套红线引擎。

inject

只注入上下文，任何判定都不做。最安全，适合第一周。

remind

写完后 PostToolUse 提醒，不阻断。出厂 maxSeverity。

ask

PreToolUse 转人工确认。仍可被 maxSeverity 压回 remind。

block

PreToolUse deny。必须过准入三条件，否则自动降为 remind。

block 准入三条件

  • 判据足够硬：仅 protect_symbol / path_only / require_tool
  • content_regex 永不 block
  • confirmed: true，否则自动降级
  • 符号类规则 symbols 非空
  • 还要受 maxSeverity 天花板压制

时机 timing

  • session_start / post_compact → 推注入
  • prompt_submit → 按任务注入
  • pre_write → 硬拦 / ask
  • pre_bash → 旁路观测
  • post_write → remind 扫描
  • stop → 交付证据

八、拦不住的明确外委，以及四条铁律

不假装能拦是底线。确定性规则归 lint，阻断合并归 CI，安全边界归宿主 permissions，过程中的「你现在要动的东西很贵」归插件。

1. pre-write 只 deny 或沉默

往写前挂提醒，会让每次正常写文件都产生干预，噪音淹没真拦截。

2. hook 只读缓存，永不建图

写前 15 秒、写后 5 秒。万文件仓建图要几十秒。缓存 miss 即放行。

3. 任何异常都必须 fail-open

hook 抛错在 PreToolUse 上等于阻断工具。为自己的 bug 挡人，比漏拦一次坏得多。

4. 没有项目层 = 零行为变化

全局层跟着插件走。没铺 .codebuddy/standards/ 的仓库，规范不进运行时。

配套铁律：未配置必须明说守卫未生效；新建公共层文件放行；查过 A 不放行 B；影响面为 0 不等于可以删；Stop 若 continue:false，同一 reason 每会话最多一次。

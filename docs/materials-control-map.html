资料分类 × 控制点写入全景

手里的资料是五类：工程文档、红线、工程图谱、技能库/知识库、门禁。CodeBuddy 能干预 Agent 的控制点是另一套：注入 / Hook / 权限 / 能力封装 / 编排。下面两张表分别回答：本工程分类有没有漏；抛开实现，这些资料该写进哪个控制点。

一、分类层面：用户五类资料 vs 本工程现有分类

比的是「有没有这一类」，不是「这一类实得到底有多深」。覆盖度：强 = 有独立配置与运行时入口；中 = 有规则条目但不是资料类型；弱 = 只有委托或空模板；缺 = 分类上不存在。

资料用户期望它管什么repo-guard 现有落点覆盖分类层缺口
编码规范怎么写代码：风格、分层、并发、类型standards/common + BE-CODE + FE-TYPE；skills backend-go / frontend-react中没有「编码规范文档」这一类。长文进了 skill，短约束进了 JSON 条目。未使用项目规则 .codebuddy/rules
接口规范契约权威源、字段字典、错误码、只增可选l0-contract + BE-API / FE-API + contracts 工具中契约文件本身不是一等配置。跨仓权威源只 inject，硬落点在 CI
提交规范commit / MR 模板 / CODEOWNERS / 不许脏代码进主干CM-VCS-001 仅 inject，landing = permissions + ci弱无独立分类。故意不在 Stop 硬拦（commit 是人的动作）
架构文档分层、目录、模块边界、系统怎么长空模板 charter.json / project-knowledge.json；repo-facts.publicLayer 是事实不是文档弱无「架构文档」类型。没有「去读哪份架构说明」的资料槽
组件规范用哪个库、何时新建、公共组件怎么改FE-LIB-* + lib_search + componentLibrary中有规则和检索，没有组件规范文档这一类

红线哪个符号不许少（protects 次数变少）redlines.json + 真 diff 引擎 + audit强只锁标识符。意图不清不在红线里，走 T4 stopConditions。人审 ask 默认关，命中后才可能弹窗
工程图谱影响面、调用链、热点、同类页图谱引擎 + 本地缓存 + 9 个 MCP + 写前 require_tool强图谱在本仓是能力不是资料。缺多仓。空图被明确禁止
技能库平台提供的 skill，开发时快速操作平台3 个工程 skill + 4 个 slash command + reviewer agent弱 / 错位现有 skill 是「怎么在本仓写代码」，不是「平台操作技能目录」。无技能注册表分类
知识库项目知识、公共知识检索project-knowledge.json 空模板；similar 从代码拉缺分类上没有知识库。设计明确不搬平台 FTS 知识库
门禁改 API / 改库 / 改 MQ / 改组件等过程闸guard L0–L6 + standards 的 severity 阶梯强（过程）与红线/规范在分类上重叠。业务门禁名（modify_api 等）刻意没建成四道独立门

本工程多出来、用户清单里没有的分类

  • 事实层 repo-facts.json：公共层、分析器、行数上限。图谱推、人确认。
  • 身份层 charter / roles：团队是谁。当前空。
  • 开发前必读 task-routes：按任务推文件路径。
  • 约束零件 禁忌 / 禁改 / 范围门 / 停止条件。
  • 治理埋点 metrics.ndjson + governance。不是资料，是门禁的反馈回路。

分类层结论

  • 五类资料里，红线、图谱、门禁在本仓有独立分类。
  • 工程文档被打散了：六种文档没有成为六类，全部挤进 standards 条目 + 两个 skill。
  • 技能库错位、知识库缺位、提交/架构几乎无类。
  • 缺口不在「再加一道 L7」，而在「文档 / 技能 / 知识」没有和「规则 / 门 / 图」平级。

二、写入前先拆：一份资料不要塞进一个控制点

CodeBuddy 的硬约束：插件只能追加上下文、在 hook 边界拦截、封装技能；权限和沙箱夺不了权。所以同一份规范必须拆成六层，分别进不同控制点。整份架构文档塞进 SessionStart 会挤爆 1500 token 预算，且注意力摊薄。

1. 索引

一句话 + 路径

让模型知道有这份东西、去哪读。进 SessionStart 或任务路由。

2. 长文

怎么做

Skill / 仓库 md。T3 只装 name+description，正文按需展开（拉）。

3. 短纪律

每次都要看见

项目规则 .codebuddy/rules 或 SessionStart 摘要。条件规则用 paths，避免常驻噪音。

4. 可判定

机器能判的才拦

符号 diff、路径 glob、本轮是否查过图 → PreToolUse deny/ask。正则只 remind。

5. 人审

判据依赖意图

PreToolUse ask（唯一能带红线文案）或宿主 permissions.ask。不要插件 deny 黑盒。

6. 合并

卡住主干

lint / CI / CODEOWNERS。插件 Stop 硬拦 commit 会妨碍人。

四、反查：CodeBuddy 五类控制点分别该收哪些资料

插件能覆盖注入 / 拦截 / 能力 / 外部接入；权限边界必须 J/U/C。不要用错类。

控制类代表节点该收的资料切片不该收
1 上下文注入CODEBUDDY.md、rules、SessionStart、UserPromptSubmit、PostCompact、output-style、--append-system-prompt架构短纪律、红线摘要、公共层清单、知识短事实、按任务「去读哪几个文件」规范全文、整张图谱、OpenAPI、技能正文
2 事件拦截 Hook24 个生命周期；过程控制最强入口。插件 hooks.json 不受 frontmatter 闸门红线拦截、图谱强制、循环、写后 remind、交付提醒、留痕、PostCompact 重注提交硬拦、shell 误伤式 deny、权限夺权、在 hook 里建图
3 权限与边界permissions.allow/ask/deny、sandbox、autoMode。插件基本无权提交规范、碰生产、危险命令。红线人审也可退到这里编码风格、UI token、接口字段冻结（应走 hook+红线）
4 能力封装skills / agents / commands / MCP / LSP / bin编码/组件长文、平台技能库、图谱工具、审查人格、slash 体检硬拦截（skill 拦不住不听话的模型）
5 任务编排workflows、agent-teams、/goal、channels、worktree多步发布门禁、远程审批中继、会话级「没做完不许停」单次写文件的红线（用 PreToolUse 更准）

# 七类规范 · 汇报稿

> 来源：references/（00 门禁索引 + 01～15 工程规范）。
> 用途：先把「规范写到哪一层、管什么、落到 CodeBuddy 哪」讲清楚。条款级细写后续再补。
> 切分原则：门禁与规范互补不重叠——能机械二值判定的进合并门禁；需要语义与权衡的进其余六类。

---

## 一、为什么是七类，不是 01～15

references 按工程主题分了 16 份（00 门禁 + 15 维规范）。repo-guard 按 Agent 执行时谁判定、写到哪个控制点分成七类：

| 七类 | 一句话 | 谁拍板 | 典型控制点 |
|---|---|---|---|
| 1 工程事实 | 代码读不出来、但每次（或碰到某类文件时）必须看见 | 人写、机器注入 | CODEBUDDY.md / rules |
| 2 技能库 | 怎么做（可挂 MCP） | 模型按任务拉 | skills/SKILL.md |
| 3 红线 | 哪个符号不许少（protects 次数变少） | 机器 deny；人审打开则 ask | PreToolUse |
| 4 过程门禁 | ReAct 内的手续与循环 | 机器 deny / remind | PreToolUse / PostToolUse / Stop |
| 5 人审 | 决定权交回人 | T4 自觉 + T7b ask | stopConditions 注入 / permissionDecision: ask |
| 6 合并门禁 | 进主干前的机械检查 | 工程侧流水线；Agent 侧宿主 | CI / pre-commit / permissions.ask |
| 7 图谱 | 代码现算的结构，何时必须查图 | 拉 + 可硬 | MCP impact/hot/similar |

01～15 不是第七类，而是技能库的主题来源；00 的 G-01～G-07 就是合并门禁清单。

## 三、七类规范大纲（汇报口径）

细条款见各层 SPEC.md。这里只保留会上要讲的「收什么 / 不收什么 / 怎么生效」。

### 1. 工程事实

- 收：环境名与隔离、公共层目录、组件库包名、权威文档路径、数据分级清单、生产资源归属（08 说扫描器看不出的那些）。
- 不收：步骤、符号禁令、「必须先查 impact」。
- 落点：短句 → 项目 CODEBUDDY.md（常驻）；按路径 → .codebuddy/rules/*.md。
- 纪律：事实要可溯源；推断必须标成推断（15§二）。

### 2. 技能库

- 收：01～14 的「怎么做」+ 15§九 的 AI 生成特有风险（过度抽象、无效用例、虚假防御）。
- 不收：二值流水线（归合并门禁）；「问人才能干」（归人审）。
- 落点：仓库根 skills/<name>/SKILL.md（T2 索引 / T6 展开）。
- 纪律：动手前先读所在模块既有实现（01）；优先复用图谱检索到的实现（15§九）。

### 3. 红线

- 收：能写成 protects + paths 的符号禁令。已发布接口字段只增不删（03/04）；凭据不得进仓（08/14）；受保护业务符号。
- 不收：风格、超时预算、覆盖率；**意图不清 / 需求多种解读**（写人审软名单 stopConditions）。
- 落点：.codebuddy/redlines.json。protects+paths 是锁，reason 是原因，必须进 git。Write/Edit 真 diff 次数变少 → deny；人审打开改为 ask。没有 protects 拦不住。
- 纪律：人写锁，机器 audit 验完整性（守空气 / paths 后门 / evidence 行号）。引擎不判断「清不清」。

### 4. 过程门禁（ReAct 内）

- 收：改公共层已有文件必须先查 impact（本插件核心）；最小改动、禁止夹带重构（03）；假设显式化、证据链、改动范围、重试上限（15）；未跑测试不得声称已测（11/15）。
- 不收：lint/CI（归合并门禁）；合入主干（归人审 + 合并门禁）。
- 落点：PreToolUse deny / PostToolUse remind / Stop 提醒（Stop 默认关，且不硬拦 commit）。
- 纪律：循环短路优先于「再去查图」；hook 内禁止建图。

### 5. 人审

- 收：需求多种解读必须停问（15§一）；合入主干 / 发布 / 生产写 / 权限变更 / 不可逆；破坏性变更与数据迁移。这些**收不成符号**，不是红线。
- 不收：未查 impact（手续，仍 deny）；循环失控、禁改清单（仍 deny）。
- 落点：
  - 软：facts.json 的 stopConditions → T4 注入，靠自觉。
  - 硬：human-review.json 打开后，红线**已经命中** → T7b ask。默认关。
- 纪律：判断在边界内外时取保守解释。合入/生产写的宿主 ask 归合并门禁。

### 6. 合并门禁（非 ReAct）

即 00 的七条，全部阻断，不通过不得交付：

| ID | 意图 |
|---|---|
| G-01 | 构建成功、无告警，依赖锁定与声明一致 |
| G-02 | 测试全过、竞态检测过、覆盖率达阈值 |
| G-03 | 格式化零差异、静态检查零告警 |
| G-04 | 单次变更规模 / 新增重复 / 未引用 / 新依赖均不超上限 |
| G-05 | 无凭据泄露，SAST 无高危 |
| G-06 | 依赖无高危漏洞、许可证合规、SBOM 已产出 |
| G-07 | 分支与提交规范、独立评审人、门禁未过不得合入、受保护分支历史未改写 |

- 落点：工程侧 = CI / pre-commit；Agent 侧 = 宿主 permissions.ask。都不是 Stop hook。
- 纪律：模型只读结论；未取得结论视为未通过；禁止改判据/调阈值/加 skip；G-04 过了不等于没有过度设计（语义仍走 01 + 15§九）。

### 7. 图谱

- 收：改公共层前查 impact；写新页/新组件前 similar / hot / lib search；接口字段从调用点反推（04）；超时与依赖拓扑（06，图不全时明确说暂不支持）。
- 不收：把规范原文存进图；在 hook 里建图。
- 落点：MCP（T2 注册，T7d 真正跑）；过程门禁可 require 本轮查过。
- 纪律：空图必须失败显式化；盲区清单必须给模型；「未查到 ≠ 不存在」（15§二）。

## 四、会上三句话

1. 01～15 是专业规范，七类是控制点分类——先决定「写到哪」，再往里填条款。
2. G-01～G-07 独占合并门禁——和规范正文不重复 ID；AI 不得预测、不得绕过。
3. ReAct 里只做人做不到的机械手续（查影响面、红线符号计数、循环止损）；问人分 T4 自觉名单与 T7b 红线命中后弹窗；lint/测试/构建放进主干前的合并门禁。

## 五、后续细写顺序（不在本次）

1. 技能库：按 01～14 各出一份 SKILL 提纲（必须 / 推荐 / 参考 三档保留）。
2. 红线：从 03/04/08/14 抽出可 protects 的符号清单（项目层填写真实字段名）。
3. 过程门禁：把 15§二～§八 收成 guard JSON 的默认关项 + 文案。
4. 人审：收不成符号的场景写 stopConditions；human-review.json 只做红线命中后的 ask 开关。
5. 工程事实：08/10 的权威源与环境标识做成 CODEBUDDY 短句模板。
